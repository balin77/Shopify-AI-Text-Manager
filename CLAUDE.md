# CLAUDE.md — Shopify AI Text Manager (ContentPilot)

Curated architectural notes for Claude Code. Public repo — nothing security-sensitive in here.

## Project

Shopify embedded app (Remix + Vite + Prisma + Polaris) for AI content generation, SEO, and multi-locale/market translation of products, collections, pages, blogs, articles, metaobjects, and theme content.

## Stack

- **Remix** (Vite) — see [remix.config.js](remix.config.js), [vite.config.ts](vite.config.ts)
- **Prisma + PostgreSQL** — schema in [prisma/schema.prisma](prisma/schema.prisma), migrations in [prisma/migrations/](prisma/migrations/)
- **Shopify App Bridge + Polaris** for the embedded UI
- **AI providers**: Anthropic, Gemini, OpenAI, HuggingFace, DeepSeek, Grok (see [app/services/](app/services/))
- **Vitest** for tests
- **Runtime**: Node, deployed on Railway from the [Dockerfile](Dockerfile); deploy mechanics as config-as-code in [railway.json](railway.json) / [railway.dbalert.json](railway.dbalert.json) / [railway.dbbackup.json](railway.dbbackup.json) (see [RAILWAY-SETUP.md](RAILWAY-SETUP.md) §0)

## Architecture invariants

- **Unified action handler.** Products, collections, pages, blogs, articles all route their actions through `handleUnifiedContentActions` in [unified-content.actions.ts](app/actions/unified-content.actions.ts). Do not add parallel handlers.
- **Translations write to Shopify AND the local DB.** Foreign values go to Shopify via `translationsRegister` (or the unstable CookieBanner endpoint) AND to Prisma (`ContentTranslation`, `ThemeTranslation`, etc.). A save is only successful if Shopify **echoes back** the keys — `userErrors` alone is not enough. Historic bug pattern: silent no-op when Shopify accepted the call but stored nothing. Conversely, always write the DB row **even when Shopify returns no digest** — `translationsRegister` requires a digest but Prisma does not (fields like `product_type` may lack one in some contexts).
- **Delete on Shopify must check the echo too — but the echo is not the only confirmation.** `translationsRemove` can silently no-op, so an unconfirmed removal must NOT delete the local DB row. The trap is that the mutation echoes what it DELETED: a key that carried no translation on Shopify in the first place (a local mirror row written when the register found no digest — the case the invariant above creates by design) comes back empty with `userErrors: []`, and the merchant was told "the translation was kept" about a field they had just cleared, with no way ever to clear it. So `removeAndVerify` RE-READS on a gap: a key that carries nothing in that locale any more is removal CONFIRMED, which is the state the rule protects reached by stronger evidence than an echo. Two rails: an ABSENT `translatableResource` is inconclusive and confirms nothing (the `translatableContent` trap again), and a MARKET override left behind does not count as the global translation surviving. The warning names the locale, the market and the unconfirmed keys — without them "sent 1, confirmed 0" cannot be told from a locale-spelling or market-scope mismatch.
- **Reload only refreshes known IDs.** Per-resource reload (e.g. `syncSingleProduct`) does not discover newly created Shopify resources. New resources appear only via full `syncAll*` runs.
- **UiDataLoader owns editor state.** [useUiDataLoader.ts](app/hooks/useUiDataLoader.ts) owns five cache refs (`deletedTranslationKeysRef`, `localTranslationsRef`, `savedPrimaryValuesRef`, `originalLoadedValuesRef`, `originalTemplateValuesRef`) plus a `resolve()` priority chain (foreign: deleted → localOverride → itemTranslation → fallback → empty; primary: savedPrimaryCache → itemField → fallback). **Items are read-only** — never mutate `item.translations` or item properties; go through the overlay refs. `resolve()` reads them.
- **Change detection uses the session load baseline**, not the live item. `getChangedFields` compares against the baseline captured at load — comparing against `item.body` etc. drifts and silently clobbers unrelated fields (e.g. a meta-description edit erasing `body_html` translations).
- **Primary saves invalidate foreign translations.** When primary content changes on templates, the server deletes stale foreign translations on Shopify. The client must invalidate `loadedTranslations`, `loadedTranslationsRef`, `localTranslationsRef`, and `deletedTranslationKeysRef` — otherwise stale foreign values reappear when switching locales. The single editor and the bulk editor (`invalidateStaleForeignTranslations`) both do this server-side too — echo-verified, global `marketId ""` rows only (market overrides survive).
- **Whether a primary change deletes its translations is a MERCHANT setting, and one module answers it.** `isPurgeOnPrimaryChangeEnabled` / `loadTranslationChangePolicy` ([translation-change-policy.server.ts](app/services/translations/translation-change-policy.server.ts)) reads `AISettings.translationPurgeOnPrimaryChange` (Settings → Übersetzungen, default on = the historic hard-coded behaviour). EVERY purge site asks it — single editor, product update, metaobjects (both routes), sub-resources, templates, and the bulk editor (`PersistDeps.purgeStaleTranslations`, checked in all three §6.6 entry points) — never the column, and never a second copy of the plan gate. It fails OPEN: a lookup error keeps purging, because a stale translation that silently survives is invisible to the merchant while a deletion is not. **The two switches are ALTERNATIVES and auto-translate wins — but only where the re-translation reaches.** `purgeOnPrimaryChange` resolves to false whenever `autoTranslateExternalChanges` is in force, decided in the module rather than only in the UI (both columns are independently writable). `purgeUnreconciledSurfaces` is the SAME question for everything no AUTOMATIC event re-translates — metaobject fields, theme content, options/option values/metafields, alt-texts, AND pages/articles/blogs/policies (reconciled only when the merchant presses reload, which is not a repair worth trading a certain deletion for) — and there the merchant's stored choice stands: "don't delete" without "will refresh" is a translation of vanished text that nobody ever corrects. `isPurgeOnPrimaryChangeEnabled(shop, db, { reconciled })` is the one accessor, `reconciled` is true for **Product and Collection only** (the two update webhooks), and it DEFAULTS to the unreconciled answer — as does the bulk editor's predicate, which is an ALLOWLIST of those two row types so a new one cannot land on the side that silently keeps stale content. A caller that wants "remove what could not be re-translated" must read neither flag — that correction belongs to the auto-translation itself (`mayPurge` in the reconciler). The Max flag `autoTranslateExternalChanges` is ANDed with the plan on every READ (a downgrade never resets the column), and its required tier lives in the client-safe [translation-change-policy.shared.ts](app/services/translations/translation-change-policy.shared.ts) so the Settings toggle and the server agree on one constant.
- **A sync repairs translations whose primary text changed where no editor of ours saw it.** Editing in the Shopify admin, another app or an import used to leave the storefront serving a translation of a text that no longer exists. `reconcileStaleTranslations` ([stale-translation-sync.server.ts](app/services/translations/stale-translation-sync.server.ts)) runs after the cache write and fixes it: echo-verified `translationsRemove` + local delete, or — on Max with `autoTranslateExternalChanges` — a re-translation of the NEW value (that flag's name is historic — it supersedes the purge, so the rows survive the in-app save and the same detection re-translates an in-app change just as it does one from the Shopify admin, another app or an import), with every entry the AI path cannot deliver falling back to the removal. **The trigger is a digest CHANGE since our own last sync**, never Shopify's `outdated` flag alone: that flag says a translation is older than its source, not WHEN the source moved, so acting on it would let one price edit (`products/update` fires for those too) delete every outdated translation a years-old translating shop ever accumulated. `loadPreviousTranslationDigests` reads the baseline BEFORE the sync overwrites it, per (LOCALE, KEY) — a digest describes the source ONE translation was written against, and two locales legitimately hold different ones; no previous digest ⇒ no evidence ⇒ nothing stale, which is what makes a first sync harmless. Every write path that stores a translation must MIRROR its digest (the product editor wrote `null` and thereby made every product translated in this app invisible to the detection). Past that gate, one of two signals must confirm the translation is really stale ([stale-translations.shared.ts](app/services/translations/stale-translations.shared.ts)): `translations.outdated` (authoritative, any key — and `false` means someone already re-translated against the new source, so it survives) or a key MISSING from `translatableContent` (= the primary value was cleared, applied only to the keys this app manages). An EMPTY `translatableContent` map is not evidence and disables the second rule entirely — a failed fetch looks exactly like "every field cleared". Global layer only; `handle` is never auto-re-translated (a slug is a URL).
- **The reconciliation is opt-in per resource, and only CHANGE EVENTS opt in.** `syncProduct` / `syncCollection` / `syncArticle` / `syncSinglePage` / `syncSinglePolicy` take `{ reconcileTranslations: true }` from the products/collections **UPDATE** webhooks (never CREATE — that is a first sync), the webhook retry + reconcile sweeps (only for a resource that was ALREADY cached), and the explicit single-item reloads. `syncSingleBlog` always reconciles: blogs have no webhook at all, so that reload is the only event that can ever notice an external change. `syncAll*` and the initial sync deliberately do NOT opt in.
- **The Max re-translation runs DETACHED, and a confirmed write is never taken back.** One AI request per locale does not fit in the HTTP request the single-item reload routes hold open, so the run is Task-tracked and not awaited (`awaitDetachedRetranslations` is the test seam); an in-flight map keyed by shop+resource stops the several `products/update` webhooks of one admin save from each starting their own run. Two rules inside it are load-bearing: a translation Shopify ECHOED back counts as registered even if the local mirror write then fails (pushing it into the failure list would purge storefront content because our own DB blinked), and a merchant save during the run (`isTranslationRecentlySaved`) abandons the rest of it rather than overwriting or deleting what they just wrote. The purge stays INLINE and runs FIRST, so the storefront is corrected immediately — and so its `markTranslationSaved` lands before the run captures its baseline: the run compares TIMESTAMPS (`translationSavedAt`), because reading the boolean made it abandon itself over its own sibling's mark. A second change event for the same resource is QUEUED behind the running one, never dropped — its entries were detected against a baseline the sync has already overwritten, so discarding them loses them for good; each run captures its "has someone else written" baseline WHEN IT STARTS, not when it was spawned, or the run it queued behind aborts it on its way out. And a run that cannot even START (a DB error on the Task row) reports `startFailed` rather than a failed list: answering a database problem with the purge would delete on Shopify while the local mirror delete fails for the same reason.
- **Theme content has exactly ONE save path.** [theme-content-api.server.ts](app/services/theme-content-api.server.ts) serves reads and AI helpers; its `updateContent` case was removed. It wrote the DB, deleted the changed keys' `ThemeTranslation` rows and never touched Shopify — a false success that left the storefront on the old primary text with the translations gone locally but alive on Shopify, and a second implementation next to `handleUpdateContent`. Nothing ever posted it (the editor page POSTs only `loadTranslations` there). Saving belongs to the host route's action via `makeThemeContentRouteAction`; do not add it back.
- **Bulk edits go through `applyBulkDiff`** ([apply.server.ts](app/services/bulk-editor/apply.server.ts)) — the ONE write path. Three entrances: the sync route action (≤`MAX_SYNC_SAVE` cells), the `seoBulkMeta` write task, and the `bulkEditorTranslate` AI task. All validate the client diff server-side against the server-built column universe (`buildServerColumnsByType` — never trust client column claims) and gate plan/locale/market at **all three** (the `/api/ai` handlers are directly POST-reachable). Foreign translations write ONLY through the echo-verified `registerAndVerify` / `removeAndVerify` / `removeAndVerifyAcrossLocales` in `bulk-editor/translations.server.ts`. Failures are per **cell** (`BulkFailure.columnId`), never all-or-nothing per row. The task type stays `seoBulkMeta` even though the editor left the SEO section — renaming would break running tasks + `LONG_RUNNING_TASK_TYPES`.
- **Image rows are the alt-text surface.** The bulk editor's `image` row type is ONE row per product medium, with the Shopify **MediaImage GID as the row id** — so the alt translation rides on the row's own `translatableResource` (key `alt`, the only one a MediaImage has; verified live via Settings → Probes → Translation) and needs no sub-resource indirection. Only the DB mirror differs: `ProductImageAltTranslation` (keyed by the ProductImage CACHE row), the same store the single editor and the SEO bulk fix write. The primary write is `productUpdateMedia` via the shared `writeMediaAltText` — the product row's `img.alt` column (main image only) uses the identical helper, so there is one mutation and one echo rule. Cached images WITHOUT a `mediaId` are excluded from the row type (no valid row id, no write path — a product resync fills it in). Collection/article featured images ARE translatable, on their own `CollectionImage`/`ArticleImage` GID with the key `alt` (re-verified live 2026-08; an earlier probe run read "zero keys" only because the sampled image had no alt text set in the primary locale — see the empty-value trap below). They are NOT in the image row type: their alt lives on the CollectionImage record, NOT on the MediaImage of the same file — the probe found the collection's file in the Files library exactly once with an EMPTY MediaImage alt while the CollectionImage alt was set, so writing the file's alt would not change the collection's. The two GIDs are also not convertible into each other (same numeric id resolves to nothing). The row type UNIONS two sources: product media (`ProductImage`, mirror `ProductImageAltTranslation`) first, then every other image of the shop from the `MediaLibraryImage` cache (mirror `ContentTranslation` with `resourceType: "MediaImage"`) — the write path picks the store by whether a `ProductImage` row exists for the GID, never by the segment. The library segment therefore DROPS rows the product segment already serves (a `usageKind` that went stale between media syncs): listing one image twice is not cosmetic — the copies would READ from different stores while both WRITE to the same one, and a translation would save and come back empty. Because that drop happens after paging, every sweep over this loader (CSV export, candidate scan) must stop on the OFFSET, never on a short page. Which write path a row takes follows the same rule as its translation store: a `ProductImage` row ⇒ `productUpdateMedia` + `ProductImageAltTranslation`; otherwise `fileUpdate` + `ContentTranslation`.
- **A media node exists before Shopify can show it, and nothing reports it in between.** `productCreateMedia` returns the GID synchronously but Shopify keeps processing the file: `MediaImage.image` stays null for seconds, and [api.product-variants.tsx](app/routes/api.product-variants.tsx) skips any node it cannot resolve to a URL — so for that window the just-saved media is reported by NOTHING, neither `mediaMap` nor the product-image list. The Image Manager used to clear its optimistic tile the moment the post-save refetch landed, which is why a fresh upload vanished from the gallery (with the media count unchanged, reading as "it was thrown away") and reappeared on the next full page load, by which time processing had finished. The fix is a THIRD tile state next to "unsaved" and "converting": `SettlingMediaEntry` ([settling-media.ts](app/components/image-manager/settling-media.ts)) — the save route returns `createdMedia` (staging URL → GID), the client keeps rendering the local preview UNDER THE REAL GID, and presence in the fetched media map is the readiness signal, uniformly for every kind (a Video/Model3d whose poster has not rendered is absent for the same reason). Three rules are load-bearing: a settling tile resolves to its real GID (`fileUrlMap` by GID for the variant galleries, `urlToGid` from the preview URL for the product gallery), so a delete, a drag into a variant or a metafield write during the window hits the right media — the ONE thing it cannot do is take part in a product-gallery REORDER, exactly like an unsaved optimistic tile, because `pendingProductImageOrder` is keyed by CDN URL and a preview URL written into it would go stale the moment the real one arrives; it does NOT count as a pending change (it is saved — the Save button must not light up again, and Discard must not throw it away); and when the bounded back-off gives up the tiles STAY. A DELETED node is retired explicitly (`handleConfirmDelete`), because it can never appear in the media map and would otherwise linger forever. Timing out means "we stopped asking", never "drop the image" — that conflation is the original bug.
- **The featured-image alt is the THIRD translation shape.** A collection's / article's `img.featuredAlt` column writes its PRIMARY value inline through `collectionUpdate`/`articleUpdate` (`image: { altText }`, the same call the single editor makes) and mirrors to `Collection.imageAltText`/`Article.imageAltText`. Its TRANSLATION is the only one whose Shopify target and DB row have different ids: Shopify stores key `alt` on the image's own `CollectionImage`/`ArticleImage` GID, while `ContentTranslation` sits on the PARENT with `key: "image_alt_text"` — exactly what `saveImageAltTextTranslation` in the single editor writes, so both editors read each other's rows. The image GID is cached nowhere and cannot be derived from the parent; `fetchFeaturedImageId` resolves it per row. `isFeaturedImageAltColumn` is the ONE predicate every branch asks (`translationKeyForColumn` returns the DB key, `persistTranslationRow` diverts before the sub-resource check, `fieldsOfGroup` maps it to `imageAltText`, and §6.6 invalidation has its own pass because neither half of the generic one can reach it).
- **A metaobject form field is `<Metaobject GID>#<field key>`, and there is ONE writer for it.** The metaobjects tab used to address a field by the bare entry GID, which is why it could edit exactly one field per entry — the label — while the bulk editor had known how to write any number of them in one echo-checked `metaobjectUpdate` for a year. The compound key ([metaobject-fields.shared.ts](app/services/metaobject-fields.shared.ts)) puts the GID in FRONT because the server recognises a metaobject form field by that prefix, and splits at the FIRST `#` (Shopify field keys are `[a-z0-9_]`-shaped, GIDs carry none). `MetaobjectTranslation` already had the field key in its unique key, so nothing migrated. `writeMetaobjectFields` ([metaobject-write.server.ts](app/services/metaobject-write.server.ts)) is the one mutation + echo + cache mirror, called by `persistMetaobjectRow` (bulk) and [metaobject-update.action.ts](app/actions/content/metaobject-update.action.ts) (single) — failures come back per `ref`, so a refused field stays red on its own instead of failing the card. Four rules ride on the field TYPE and none of them is cosmetic: `color` and `file_reference` are writable but carry `translationKey: ""` (one value per shop — down the foreign chain they resolve to `""` and the next save CLEARS them, the merchandising-attribute rule verbatim); `rich_text_field` is read-only and SKIPPED silently on a primary save (the form echoes back the plain-text preview it was shown, so erroring would fail every save on such a definition and writing would replace Shopify's JSON with its own preview); an empty value always means CLEAR, with Shopify's required-field validation doing the refusing; and a type with no editor is NAMED with its type on the card, never dropped. That `translationKey: ""` also collides with `isAttributeField`, which recognises a merchandising attribute by exactly `translationKey: "" + supportsTranslation: false` — so a colour, a file reference and a taxonomy reference were routed out of their entry's card into the page-wide "Details" card at the bottom, and the card header's colour swatch, which picks its control out of the group's own fields, never found one. **A field that names a `groupId` is never an attribute** (the veto lives in [content-attributes.shared.ts](app/services/content-attributes.shared.ts)): where a grouped field renders is its group's business, and the seven real attributes name no group. The sync's label-only translation filter is gone — mirror what Shopify reports, and never read a MISSING key as "not translatable" (the `translatableContent` trap). `MetaobjectTranslation.type` is the BARE type: it used to be `itemId`, i.e. `metaobject_type_<type>`, which the definition stale-delete removes by construction. MEASURED on a live shop (2026-08-18, API 2026-07, [PLAN_METAOBJECTS_EDITOR](docs/plans/PLAN_METAOBJECTS_EDITOR.md) §2.1) and worth knowing before designing anything else here: `shopify--color-pattern` carries `label:single_line_text_field*`, `color:color`, `image:file_reference`, `color_taxonomy_reference:list.product_taxonomy_value_reference*` and `pattern_taxonomy_reference:product_taxonomy_value_reference*` (`*` = required), so **a colour entry cannot be CREATED from this app** — two required fields are taxonomy references this app has no editor for, `metaobjectCreatability` answers `unsupportedRequiredType`, and the create form offers the type DISABLED with that reason rather than dropping it. Editing, translating and deleting are unaffected. Shopify reports **only `label`** as translatable on that definition, and that is a real negative rather than the empty-value trap: `color` and both taxonomy fields were FILLED in every sample and still absent, which is what makes `translationKey: ""` for a colour the measured answer instead of the careful one. Every standard definition reports `access.admin = PUBLIC_READ_WRITE`, and writing one is MEASURED to work (V1, 2026-08-19: create + colour update confirmed by a fresh read), so the §7.2 read-only branch fires nowhere on such a shop — it stays wired for a definition that does refuse. The storefront swatch IS derived from the entry's `color` field (V3, same run): `metaobjectUpdate` on it moved `ProductOptionValue.swatch`, so the editor may promise that.
- **The taxonomy reference that blocks creation is measurable, and the block is this app's, not the platform's.** A `product_taxonomy_value_reference` field names its attribute by a stable **HANDLE** in its own `validations` (`product_taxonomy_attribute_handle`), and the permitted values are reachable through the CATEGORY, which is the only door `Taxonomy` has: `TaxonomyCategory.attributes` → a union whose `TaxonomyChoiceListAttribute` member carries `values { id name }`. MEASURED on a live shop (2026-08-19, API 2026-07, [PLAN_METAOBJECT_TAXONOMY_CREATE](docs/plans/PLAN_METAOBJECT_TAXONOMY_CREATE.md) §1.3): `color` has **19** values, `pattern` **51**, both complete, and every value real entries already hold is in the offered list — so the picker is a LIST, not a search, and matching the attribute by NAME (the union member exposes no `handle`) is confirmed rather than assumed. The ten sampled categories reported "Color"/"Pattern" repeatedly but under **one id each**, so "the permitted values" does not depend on which category was sampled. Two rules for anything built on this. The query is **cost-bound**: `categories(10) × attributes(50)` is ~500 points against the Admin API's 1000-point single-query ceiling, and the first cut's `categories(25) × attributes(50) × values(250)` came back `MAX_COST_EXCEEDED` — which the probe then reported as "no path exists", the failed-call-as-negative-answer trap. And the shape is per **FIELD**, never per definition: `shopify--color-pattern` has two taxonomy fields, a pattern value can never be in the colour attribute's list, so a shared bag of GIDs checked against one list reports "not covered" by construction. Nine further standard definitions on that shop (`material`, `shape`, `vase-shape`, `bag-case-material`, …) carry exactly ONE such required field, so the same editor unblocks creation for all of them — the payoff is not just the colour. **Built** as [taxonomy-values.server.ts](app/services/taxonomy-values.server.ts) (the lookup, memoising successes for an hour and failures never — one throttled minute must not become an hour of "this field has no values"), [api.metaobject-taxonomy.tsx](app/routes/api.metaobject-taxonomy.tsx) (self-gating; the attribute handle is read SERVER-side out of the cached definition, so the client names a type and a field key and never an attribute) and `TaxonomyValuePicker` ([TaxonomyValueField.tsx](app/components/metaobjects/TaxonomyValueField.tsx)) — ONE control rendered by both the entry editor and the create modal, because two would come to write different bytes into one field. Four rules ride on it. The DISPLAY form IS the stored form (a JSON array of GIDs, or a bare GID): the control speaks GIDs and paints names beside them, and every lossy round trip in that module has been a bug. A value that is not a `TaxonomyValue` GID is refused by BOTH write paths before the mutation — it fails at the GraphQL SCHEMA level, a top-level `errors` array with `data: null` that never reaches `userErrors`, so forwarding it makes the whole save read as a success while nothing was written. A stored value the offered list does not contain stays VISIBLE (its own `Select` option, its own chip), because an empty control is the one outcome that makes the next save clear real data. And the list is fetched ONCE per (type, field) through a module-scope promise, or a page of 25 colour entries would fire 25 identical sweeps. `EDITABLE_METAOBJECT_FIELD_TYPES` now deliberately DIVERGES from `isEditableMetaobjectFieldType`: "can a form collect this?" and "can a spreadsheet cell hold this?" are different questions, and the taxonomy reference is exactly where they part — the create form has a picker, the bulk grid has none and is kept out of it on purpose.
- **Deleting a metaobject entry: Shopify is the guard, and this app only names the number first.** `countLinkedOptionUsage` ([metaobject-usage.server.ts](app/services/metaobject-usage.server.ts)) is three-valued on purpose: an empty product cache, a truncated scan and a failed lookup all answer `known: false`, because "0 products" and "we cannot tell" look identical in a number. The three values are REPORTED; only a KNOWN non-zero one blocks — reporting an uncertainty and refusing on it are different things, and which of the two is right depends on what the platform does, measured below. It scans only options that ARE linked (`linkedMetafieldKey` set) and matches `linkedValue` on the PARSED JSON, never as a substring on the text column. What Shopify does to a product whose option value points at a deleted entry was PLAN_METAOBJECTS_EDITOR V5 and is now MEASURED (2026-08-19, [api.metaobject-probe.tsx](app/routes/api.metaobject-probe.tsx)): it **REFUSES** — `The metaobject cannot be deleted while it is referenced by another resource.` No option value disappears and no variant is destroyed, so the platform is the real guard and this app's check is a courtesy that names the number before Shopify names the rule. That is why UNKNOWN usage no longer blocks: it did while V5 was open, which was right then and is a dead end now (a shop with no cached products could never delete an entry, and no sync would change the answer). A KNOWN usage still stops early. The dialog says the measured thing rather than the old worst case — an invented consequence is not a safer warning, only a false one. The client-side lock is UI: that route takes a direct POST. `Metaobject.referencedBy` is the LIVE cross-check and it beats the cache wherever it answers (`liveMetaobjectUsage`), because it is what predicts Shopify's refusal: the platform declines on ANY reference while the cache counts option VALUES only, so the cache can read zero where the delete still fails. Measured 2026-08-19: a `MetafieldRelationConnection` paging through `nodes`, whose `referencer` resolves to a **Product** — while its sibling `target` does NOT resolve on a live shop (`Metafield reference target could not be retrieved`), and one unresolvable field fails the whole query, which is why nothing selects it. There is **no count field**, so counting means paging: it is asked ONCE for the one entry being deleted, a full page reports "n or more", the card's list keeps reading the cache, and a failed query is `known: false` — never zero. Related: a metaobject TYPE row (`metaobject_type_<type>`) is not a deletable object at all, and `resourceOfItem` returning the tab's single create-resource for ANY id is how it grew a Delete button that 400s *after* the merchant typed the type name into the confirmation.
- **A metaobject's completeness is asked by COMPOUND key, and asking by the bare GID is how the language buttons pulsed forever.** `metaobjectTranslatableFields` ([metaobject-fields.shared.ts](app/services/metaobject-fields.shared.ts)) is THE enumeration behind "does this locale still need work": every TRANSLATABLE field of every entry, as `<gid>#<fieldKey>`. Three separate places in [field-validation.utils.ts](app/utils/field-validation.utils.ts) used to look for a translation stored under the bare metaobject GID — correct while the GID WAS the field key, and permanently wrong from the moment the editor learned to address a field compoundly. Nothing writes a bare-GID key any more, so every entry read as untranslated in every locale forever: the locale buttons pulsed blue, the tooltip listed the whole type as missing, and the item-list dot stayed on, on a shop with nothing missing. The per-FIELD marker carried the MIRROR image — it matched a compound key against an entry id, so it never fired even where a translation really was absent. Colour, file and taxonomy fields are excluded (one value per shop, no per-locale form at all) and so is rich text (read-only), or the pulse would simply be permanent for a different reason — as it would for a definition whose Shopify **Translations capability is switched off**, which is why `MetaobjectDefinition.translatableCapability` is synced and read three-valued: a KNOWN false takes the type out of the count, `null` (row predates the column) keeps counting, because hiding a real missing translation behind a guess is the worse of the two errors. The enumeration is memoised on the entry array's identity: it runs once per rendered FIELD and the editor re-renders every card on every keystroke, so on 25 entries with a ten-field definition it was ~62 500 spec constructions per keypress. Two neighbouring rules on the primary side: the overlay is keyed compoundly there too (a bare `"label"` lookup silently missed and fell back to server data, so a just-filled entry still counted as empty), and a definition that names no label field is NOT an empty entry — the label keys are a naming convention, and reporting their absence as missing content made the orange pulse permanent for such a type.
- **Sub-resource translations ride on their OWN Shopify resource.** Metafield cells translate on the **Metafield GID** (key `value`), option names on the **ProductOption GID** and option values on each **ProductOptionValue GID** (key `name`) — never on the product's `translatableResource`. `translations.server.ts` owns the mapping (`isSubResourceColumn` / `subResourceTargetsForColumn` / `subResourceCacheFromRow`), `apply.server.ts` writes it through `persistSubResourceTranslations` with the same echo/digest rules as the row path, and `ContentTranslation.resourceType` is `Metafield` / `ProductOption` / `ProductOptionValue` — the exact strings the single editor writes, so both editors read each other's rows. A primary change to a metafield or option invalidates ITS OWN translations (same §6.6 rule, own resource id). An option-VALUES cell is ONE cell over N resources: it is written as a whole list, so the AI path merges over the entries that already have a translation instead of replacing them. Alt-texts are deliberately excluded (they ride on MediaImage and even the primary write needs the deprecated `productUpdateMedia`).
- **`translatableContent` only lists keys that HAVE a primary value.** A resource with an empty field returns no entry for it, which is indistinguishable from "this resource type cannot translate that field" — the trap that produced the wrong "collection/article images are not translatable" invariant above. Never conclude "not translatable" from an empty key list: probe a resource whose field is actually filled (`pickWithImage` in [api.translation-probe.tsx](app/routes/api.translation-probe.tsx) picks an alt-bearing sample for exactly this reason), or the answer is inconclusive, not negative.
- **A merchandising attribute is only readable once `attributesSyncedAt` is set.** `Product`/`Collection`/`Article`/`Page` carry a block of attributes the sync only learned to fetch in PLAN_CONTENT_CREATION Phase 0 (`vendor`, `tags`, `category*`, `templateSuffix`, `publishedAt`, `sortOrder`, `isSmart`/`sourcesJson`, `author`, `isPublished`, plus the `ProductCollection` membership rows). On a row written by an older sync those columns hold the migration DEFAULTS — `null`, `{}`, `true` — which is indistinguishable from "the merchant left it empty", the same trap as `SeoCrawlPage.metaRobots`. `attributesSyncedAt` is the discriminator and `attributesKnown()` in [attribute-sync.shared.ts](app/services/attribute-sync.shared.ts) is the gate every reader passes through: unset ⇒ show "unknown" and offer a reload, never a red "missing". The WRITE side enforces the mirror image: the mappers there return `{}` for a response that did not carry the block, so a partial query can neither overwrite what a full sync established nor stamp knowledge that never arrived — and `productCollectionRows` returns `null` (skip the rebuild) rather than an empty list (wipe the memberships). That module is also the ONE place where the attribute GraphQL selections live, and **there are FOUR product write paths, not one** — `syncAllProducts` and `syncProduct` in [product-sync.service.ts](app/services/product-sync.service.ts) (the latter is also what the `products/*` webhooks call, so that one is covered) plus the two route-local ones in [api.sync-products.tsx](app/routes/api.sync-products.tsx) and [api.sync-missing-products.tsx](app/routes/api.sync-missing-products.tsx). Each carries its OWN inline product query, so a new product column has to be added to every one of them; interpolating the shared constants is what keeps that mechanical instead of a memory exercise. A path that fetches a NARROWER selection is handled, not trusted: the mappers require EVERY key of the block to be present and return `{}` otherwise, because a half-delivered block written as defaults is worse than no write at all. `Collection.sourcesJson` stores a `{shape, apiVersion, data}` envelope, never a bare tree: the 2025-10 `ruleSet` and the 2026-07 `sources[]` models are not interchangeable and a reader must not have to guess which one a row holds.
- **`Collection.ruleSet` is a LOSSY back-projection of the 2026-07 `sources` model, not a second view of it.** Measured on a live shop (2026-08, Settings → Probes → Collection Model): a source written as `productTag { relation: TAGGED_WITH, values: […], matchType: ANY }` reads back through `ruleSet` as `{column: "TAG", relation: "EQUALS", condition: "…"}` — the relation is coerced and the condition's OWN `matchType` (the new model has two levels of it, one per source and one per condition) is dropped entirely. Structures with no legacy equivalent at all — exclusions, multiple named sources, variant targeting — cannot project and are simply absent; that is the same mechanism behind the documented "collections using new features are filtered from pre-2026-07 query results". So from 2026-07 on, READ `sources`, never `ruleSet`: an editor that reads `ruleSet` and writes it back would silently change a collection's membership, which is the §2.4 read-only rule one level deeper. Editing a source is also a DIFF, not a replace (`conditionsToCreate`/`ToDelete`/`ToUpdate` + `selectionsToAdd`/`ToRemove`, each keyed by an id from the read path), which is what makes "don't touch what you cannot render" mechanical rather than a discipline.
- **A menu item's translation rides on a `Link` GID whose NUMBER is the MenuItem's — and `nestedTranslatableResources` does not hand it over.** Measured on a live shop (2026-08, Settings → Probes → Translation, [api.menu-translation-probe.tsx](app/routes/api.menu-translation-probe.tsx)), identically on **2025-10 and 2026-07** — the new API version changes nothing here, because nothing needed changing. Three results, and the middle one is the whole story. (1) `translatableResource(<Menu GID>).nestedTranslatableResources(resourceType: LINK)` returned **0 links for every menu** — not "only the first level", ZERO, at every depth, on both versions. The documented one-level-of-nesting caveat understates it: that path yields nothing at all, so an implementation that trusts it concludes menus are untranslatable. (2) The flat `translatableResources(resourceType: LINK)` sweep returned **59 links for 59 menu items across depths 1, 2 and 3 — absent: 0 at every depth**, and every sampled `gid://shopify/MenuItem/<n>` resolved as `gid://shopify/Link/<n>`, SAME NUMBER, with a matching `title`. The id is derivable; no enumeration and no title matching is needed to address a child. (3) Sub-level links already CARRY translations written by Shopify's own editor (`Design-Vasen` → `Designer Vases` at depth 2), so the resource stores foreign values rather than merely reporting them. Depth is not the discriminator anywhere in this: depth-3 items behave exactly like depth-1 ones. The only key is `title` — a link's URL is not translatable, and lives under the locale prefix instead. (4) And THIS app's own write is confirmed end to end: `translationsRegister` on the derived Link GID of a depth-3 item echoed the value back, a FRESH read returned it, and `translationsRemove` took it away again with the removal echoed — the full register/verify/remove cycle the translation invariants demand, on the deepest level the shop has. So nothing about menus is a platform limit; the only broken thing was the enumeration, and the fix is to stop asking for it: sweep `translatableResources(resourceType: LINK)` for the shop and address each item by the GID derived from its MenuItem id. Two things stay UNMEASURED and must not be assumed: whether a translated sub-item actually RENDERS in the storefront navigation (Shopify's own editor writes the same resource, so this is likely rather than known), and whether a market-scoped (`marketId`) menu translation behaves like the global one.
- **Pages, articles and blogs have NO Shopify webhook — the editor's save is the only moment anything knows.** Products and collections are covered by `products/update` / `collections/update`, so [webhooks.products.tsx](app/routes/webhooks.products.tsx) enqueues IndexNow from them; for the other three a published page reached IndexNow only via a manual catalogue send. `shouldEnqueuePublishChange` ([index-now.service.ts](app/services/seo/index-now.service.ts)) mirrors `shouldEnqueueProductChange` deliberately — live now ⇒ submit; just became a 404 ⇒ submit, because reporting removals is half of what IndexNow is for; never live ⇒ nothing, since a draft's URL is an address no engine holds. That last rule is why the enqueue sits at the TRANSITION and not at create: everything this app creates is created unpublished, so a create-time ping could only ever announce drafts. `previousPublished` comes from the cache and is reported as UNKNOWN when `attributesSyncedAt` is unset — the column defaults to `true`, so reading it as "was visible" would make the first save of every draft look like a publish. [index-now-content.server.ts](app/services/seo/index-now-content.server.ts) owns it, keeps the URL building pure and testable, and never throws: the save has already happened.
- **On a primary-locale save, a field's PRESENCE is not the merchant's INTENT.** `buildFieldsForSave` ([useEditorAutoSave.ts](app/hooks/useEditorAutoSave.ts)) filters to changed fields only for FOREIGN locales; a primary save carries every field the config declares. For text that is harmless — writing the same title back changes nothing. For the §Phase 3 merchandising attributes it is data loss, because Shopify REPLACES rather than merges and the values arrive from a cache that may never have been attribute-synced: a title edit would delete every tag, clear the vendor, reset the theme template and PUBLISH a hidden article. `changedFields` is the discriminator and `attributeInputFor` ([content-attributes.shared.ts](app/services/content-attributes.shared.ts)) is the gate — no `changedFields` ⇒ write no attributes, because a caller that does not say what changed is indistinguishable from one where nothing did. `productType` in [update.actions.ts](app/actions/product/update.actions.ts) has carried this exact guard since long before those fields existed; it is the precedent, not an exception. The same module is also the ONE place that validates them: `status` and `sortOrder` are GraphQL ENUMS, and a bad enum fails at the SCHEMA level — a top-level `errors` array with `data: null` that never reaches `userErrors`, so a forwarded bad value makes the whole save read as a success while nothing was written. Unrecognised values are dropped and reported. And an attribute a resource does not have is filtered out rather than sent: `sortOrder` on a page makes Shopify reject the WHOLE input, taking the merchant's text edits with it. UI side: these fields carry `translationKey: ""`, which `resolve()` short-circuits to the primary value — sent down the foreign chain they would resolve to `""` and a Polaris `Select` would render its first option, showing an ACTIVE product as DRAFT and a hidden page as visible.
- **A handle change owes the old URL a redirect, and the redirect is a DIFF over the shop's existing ones.** Changing a handle silently 404s every link to the old address, so both primary write paths — the single editor's `updateContent` and the bulk editor's `field.handle` column — run the same decision through [handle-redirect.shared.ts](app/services/seo/handle-redirect.shared.ts) (pure) and [handle-redirect.server.ts](app/services/seo/handle-redirect.server.ts) (Shopify). Four rules are load-bearing. (1) The target is the handle Shopify **echoed back**, not the one submitted: every write path sanitizes the slug and every update mutation already selects `handle`, so trusting the sent value is an assumption whose failure mode is a redirect onto a 404 plus a message saying the old URL is covered. (2) It is a diff, never a blind create: renaming a→b→c must REPOINT `/a→/b` to `/a→/c` (otherwise this app's own `redirect-chains.ts` reports the chain it just made), and renaming back a→b→a must **delete** `/a→/b` — that path is a live page again and Shopify serves the redirect in preference to it, so leaving the row makes the renamed object unreachable at its own address. Lookups go through `listRedirects(query)` and are re-filtered by exact path, because the query is a search and a near-miss must never be repointed. (3) It can never fail the save: the content update has already happened, so every failure is a NOTE and both call sites catch. (4) TRANSLATED handles are covered too, on the strength of a measurement: **2026-08 on a live translating shop** ([api.redirect-locale-probe.tsx](app/routes/api.redirect-locale-probe.tsx), Settings → Probes → Translation), a throwaway `/<probe>` → `/<target>` with both sides distinctive answers BOTH halves of the question — `/en/<probe>` returns 301, so a locale-prefixed path DOES match the path-based redirect table, and its `Location` is `/en/<target>`, so the prefix is CARRIED onto the target. ONE UNPREFIXED row therefore serves every locale, and `decideTranslatedHandleRedirect` writes exactly that from the bulk grid's foreign `field.handle` cell and the single editor's foreign save. That same reach is what makes it delicate — the row fires under EVERY prefix, including locales nobody edited — so it refuses five things: a locale that had **no previous translation** (it was being served under the PRIMARY handle, which stays live; this is also why bulk-translate, which only ever FILLS empty values, creates none), an old handle that is still the primary one, **another locale's** handle of the same resource, or **another RESOURCE's primary handle** (all three would hijack a live page — and the last has no counterpart on the primary path, where Shopify's own handle uniqueness makes a renamed-away handle free by construction, which is why `handleTakenByOtherResource` exists and why an UNKNOWN primary handle refuses outright instead of proceeding), a **market-scoped** translation (a shop-wide row cannot express a per-market URL), and an **article under a blog whose own handle is translated** (two translatable segments, and which spelling the storefront serves is unmeasured — reported as `localeBlogHandleUnknown`, never guessed). A CLEARED translation redirects back to the primary handle. Two mechanics carry the weight: the old handle is captured BEFORE the write (both write paths upsert `ContentTranslation` themselves, so a capture placed after reads its own write and every rename looks `unchanged` — that is how the first cut shipped dead), and the NEW handle is the one Shopify **stored**, never the one submitted (`registerAndVerify` now returns `confirmedValues`; the single editor re-reads the row) — the generic write path silently SKIPS a handle translation equal to the primary handle, so a submitted value can describe an edit that never happened. Two residuals, stated rather than hidden: a collision with a different resource's TRANSLATED handle in another locale is not checked (`ContentTranslation.value` has no index and the scan would run per row on a path that writes hundreds), and two locales sharing a slug are decided by whoever writes last, since one path holds one redirect. Keep the probe route: this is re-measurable in one click rather than re-argued. Blogs redirect their own `/blogs/<handle>`, but their ARTICLES' URLs move with them and Shopify redirects have no wildcards, which is why that case reports `blogArticlesUncovered` rather than a plain "created". Notes travel as CODES ([handle-redirect-message.ts](app/utils/handle-redirect-message.ts) owns the wording) — the app ships in three languages, and the save response is read in two places.
- **Storefront URLs handed to an external system use the PRIMARY domain.** Shopify 301s every storefront URL on `*.myshopify.com` to the shop's primary domain, so a myshopify URL published outwards is a non-canonical redirect — and for a host-verified protocol it is worse: the verification fetch ends on a different host than the one declared, which is what IndexNow's ownership check is about (it cost this app a feature that could not work on any shop with a custom domain). `fetchPrimaryDomain` in [shop-domain.server.ts](app/utils/shop-domain.server.ts) is THE resolver (sitemap + IndexNow use it; the crawler and AEO carry their own equivalent). IndexNow additionally PERSISTS the resolved host on `SeoIndexNowConfig.host` so webhooks can build URLs without a lookup, and re-syncs it on every section visit — a merchant who connects a custom domain later is corrected without minting a new key.
- **`/agents.md` is the canonical AI-discovery file; `/llms.txt` only mirrors it.** Shopify serves both by itself (since ~2026-05) and a theme template overrides each path independently, so writing only `templates/llms.txt.liquid` — what this app did — leaves the file agents actually read at the platform default. `generateAndUpsertAiDiscovery` ([aeo.service.ts](app/services/seo/aeo.service.ts)) therefore writes BOTH in one action: writing one leaves the shop half-overridden in a way nobody predicts from a button labelled "generate". `agents.md` is a DIFFERENT document, not the same bytes twice — it links the policies (a buying agent's actual questions) and states where price and availability are authoritative, because a periodically regenerated file is exactly what an agent must not quote a price from. And every claim about these paths is MEASURED: a successful `themeFilesUpsert` proves the file was stored, not that the URL serves it, so `probeAiDiscoveryDelivery` fetches the live URL and the UI distinguishes five states (ours and live / stale / stored but not served / Shopify's default, with an excerpt of what IS served / unreachable). "Remove our version" deletes the template and hands the path back to the platform — an override the merchant cannot undo in the app is one they must undo in the theme code editor. `llms-full.txt` is deliberately NOT written: our copy is capped at 50 entries per type, so overriding Shopify's full catalog dump with it would be a regression. All writes stay behind `AEO_THEME_WRITES`; the measurement is read-only and works without it. **Exactly ONE part of either document is the merchant's: the opening paragraph** (`AISettings.aiDiscoveryIntroAgents` / `…Llms`, editable in the section with an "improve with AI" pass that suggests INTO the box and never past it). The catalog sections stay generated, because a hand-edited product list is stale at the next price or handle change and `refreshLlmsTxtIfStale` would overwrite it anyway — while the intro is the one thing no query can know (who is behind the shop, where it ships). It is read inside `buildAiDiscoveryForShop`, not passed in per caller: the staleness comparison, the background refresh and the generate button all go through that builder, and an intro reaching only one of them would report the file stale forever. It REPLACES the generated opening sentence rather than stacking on it, a whitespace-only value is stored as NULL (so "never written" and "deleted" stay distinguishable), and it rides the same `defangLiquid` + `{% raw %}` wrapper as everything else in the file.
- **The weekly crawl and the manual one start through ONE path.** [crawl-run.server.ts](app/services/seo/crawl-run.server.ts) owns single-flight, the `Task` row, snapshot retention, the detached runner and the failure bookkeeping; the route handler is only the HTTP shell and `SeoCrawlAutoRunService` calls the same function — an unattended run that drifts from the observed one is a bug nobody would see until a merchant compares them. Weekly (not nightly like the audit) because the audit reads the DB cache while the crawl fetches every page of the merchant's own storefront; the per-tick batch is correspondingly small (3), since each start keeps fetching for minutes after the tick returns. `lastAutoCrawlAt` is its own column: one stamp cannot express two cadences. A shop whose crawl is already running is stamped and SKIPPED, never crawled twice.
- **A detached run's single-flight must not outlive its process.** The crawl is a fire-and-forget promise inside the web process, so a Railway redeploy of a new app version (or an OOM kill) kills the runner while BOTH rows it owns still say `running` — and nothing ever writes their terminal state. That is a hang, not a stale label: `startCrawlRun` refuses every new crawl, the crawl page shows a scan that never finishes with the button disabled, the weekly sweep stamps and skips the shop, and because pages are persisted in ONE bulk insert at the very end, the newest `SeoCrawlSnapshot` is an EMPTY one that hides the last complete report. The old safety net was the reaper's 45-minute `LONG_TASK_TIMEOUT_MS`, i.e. three quarters of an hour of exactly that, and it never touched the snapshot at all, so that row stayed open for good. [orphan-run-recovery.js](orphan-run-recovery.js) is the ONE place that decides a run is dead — a root module importing nothing and taking the Prisma client as an argument, because the boot recovery ([task-recovery.service.js](task-recovery.service.js), outside the React Router bundle) and the app itself ([crawl-run.server.ts](app/services/seo/crawl-run.server.ts), inside it) must not each carry their own copy. Four rules: a **HEARTBEAT type** (`seoCrawl` — it writes `Task.progress` at least every 10s inside the fetch loop, at every boundary of the post-crawl tail, and throughout the external-link pass) is reaped after a 5-minute silence instead of 45 minutes, and a type that may legitimately go quiet between two provider calls must NOT be listed there — the cost of a threshold that is too short is not a late cleanup but a LIVE run reaped mid-flight, its snapshot closed under it and single-flight opened for a second crawl of the same storefront, which is why the tail got its beats in the same change; at BOOT the age check is dropped entirely, since a detached runner cannot outlive its process; `startCrawlRun` TAKES OVER a run that has been silent past the threshold rather than refusing the merchant standing in front of it, and closes the old snapshot BEFORE creating the new one (the snapshot rule recognises an orphan by "this shop has no running crawl task", so a new running snapshot created first would look live); and a sweep from a REQUEST is scoped to its own shop — an unscoped one would fail another merchant's live crawl. The snapshot is marked `failed` with `error: "interrupted"`, never deleted (deleting rows to hide a failure leaves the merchant with no explanation for why nothing changed), and the merchant sees it as a WARNING with its own text: nothing is wrong with their storefront, and a red "try again" over our own restart sends them looking for a fault they do not have. **RESUMING an interrupted crawl was considered and dropped** (2026-08-19): `runCrawl` keeps its entire state in memory — `pages`, `visited`/`discovered`, the BFS frontier, `inboundCounts` and the raw `edges` list — and persists in ONE bulk insert at the very end, so an interrupted run leaves literally nothing to resume FROM. A real resume needs durable checkpointing of the frontier plus the discovered/inbound state, i.e. new tables and DB writes inside the hottest loop in the app, and the raw edge list is the part that is deliberately never persisted (only capped `SeoCrawlBrokenLink` rows are) because it is links-per-page, not pages. It also breaks what a snapshot IS: `diffCrawls` compares two runs as two points in time, and a run stitched together across a deploy is neither. So the answer to "the crawl hung" stays RESTART, made cheap and immediate by the recovery above — not resume.
- **Catalog readiness reports five fields and nothing another section owns.** Shopify Spring '26 syndicates eligible products to the AI channels by itself, so completeness — brand, category, GTIN, description, image — is what decides whether a product is picked up ([catalog-readiness.service.ts](app/services/seo/catalog-readiness.service.ts), AEO step 3). SEO titles, meta descriptions and alt coverage stay with `analyzeStore`: two scores for one product in two tabs help nobody. Two traps are honoured rather than worked around — `attributesSyncedAt` gates `vendor`/`categoryId` (one unsynced row in the scanned window ⇒ BOTH buckets are dropped and the UI explains why, because a migration default is indistinguishable from an empty field), and only ACTIVE products are scanned (DRAFT is published nowhere and UNLISTED is deliberately link-only — reporting either as a syndication gap reports merchant intent as a defect, the same rule the llms.txt query follows).
- **AI-referral tracking stores a source key, never a referrer.** The beacon reports a click that came from an AI assistant; [proxy.ai-referral.tsx](app/routes/proxy.ai-referral.tsx) classifies it SERVER-side (the route is directly POST-reachable, and a referrer can carry a conversation id or a search term that must never reach the database) and writes one aggregate row per (shop, source, UTC day, landing path). No cookie, no identifier, no IP. The referrer DECIDES wherever there is one and `utm_source` is consulted only in its absence: the parameter is copyable, so a ChatGPT link pasted into a newsletter would otherwise report that newsletter's clicks as ChatGPT visits forever. Two limits are stated in the UI instead of being hidden — Google AI Overviews arrives as an ordinary `google.com` referrer and is NOT counted, and a stripped referrer cannot be classified at all. Undercounting is the chosen failure mode. The theme-side token list is a loose PREFILTER to keep normal traffic off the endpoint; the server list is the authority, so a token missing there costs a missed visit, never a wrong one. The beacon rides in [web-vitals.js](extensions/storefront/assets/web-vitals.js) behind the **Web Vitals (RUM)** embed, NOT in the JSON-LD block where it started: JSON-LD is markup a merchant may legitimately switch off, and switching off markup must not silently switch off a measurement. It is its own IIFE — the vitals collector returns early without `PerformanceObserver`, and a referral is still worth counting on such a browser. Which embed carries it is stated in the UI, because "0 visits" and "the embed is off" are indistinguishable from the report. **Claude is a measured blind spot**: its links pass on neither a referrer nor a `utm_source`, so a click from claude.ai is indistinguishable from a direct visit (ChatGPT and Perplexity arrive fine). Stated in the caveat rather than left as a puzzle.
- **Readability is reported, never scored — and the number only appears where a formula exists.** [readability.ts](app/utils/readability.ts) always computes the structure findings (sentence length, paragraph length, missing subheadings), which hold in every language, and produces a reading-ease value ONLY for the three languages with a validated formula (Flesch/EN, Amstad/DE, Fernández-Huerta/ES). For every other locale it returns `null` plus an explanation: an English formula over another language is not a rough estimate, it is a wrong number with a familiar name. It analyses the language the editor is CURRENTLY showing (`contentLocale`, the real locale — not `keywordLocale`, whose `""` means "primary"). It deliberately stays out of `computeSeoScore`: folding it in would silently move every shop's score — which is also why it renders as its OWN bordered section BELOW the score details with its OWN `seoSidebarReadability` help icon, and why the number names its formula in place: stacked among the score's findings it read as part of the number, and an unnamed 0–100 badge invites the cross-language comparison it cannot support (German scores lower than English on the same text because German words carry more syllables). Passive-voice and transition-word checks are out for the same reason the rest is in — they need per-language word lists to be anything but noise.
- **An IndexNow key file must sit at the storefront ROOT — measured, not assumed.** Serving it from the app proxy (`/apps/contentpilot/indexnow-key`) works as delivery (probe on a live shop: 200, no redirect, content matches) but every submission still comes back `422 InvalidRequestParameters — "not related to your site verified through the keylocation parameter"`, because a non-root `keyLocation` verifies only its own sub-path. It is a SCOPE rule, not a host rule: do not re-diagnose it as a domain problem. So `keyLocation` names `https://<host>/<key>.txt` and a Shopify **URL redirect** maps that root path onto the app proxy — one host end to end, no `cdn.shopify.com` hop (a cross-host hop is what an ownership check objects to). Confirmed working on a live shop: `/<key>.txt` → 301 (same host) → app proxy → 200, submission **202 Accepted** — the engine does follow a same-host 301, and a root keyLocation covers the whole site. Lifecycle + echo rule in [index-now-key-file.server.ts](app/services/seo/index-now-key-file.server.ts); the redirect GID lives on `SeoIndexNowConfig.keyRedirectId`, and both the section loader and the sweep recreate it when it is missing. [api.indexnow-probe.tsx](app/routes/api.indexnow-probe.tsx) (Settings → Probes → Translation) fetches the key file hop by hop and fires one real submission, so this stays re-measurable in one click rather than re-argued.
- **One crawl, two STEPS of one tab.** `runCrawl` ([crawl.service.ts](app/services/seo/crawl.service.ts)) stays the ONLY live-fetch surface. `/app/seo/crawl` shows both halves behind `?view=delivery|onpage`, as two `StepTile`s (the AEO section's shape, and the same relationship: a page that is not delivered has no on-page quality to judge). They were two nav chips at first — which only made merchants ask which of the two crawls they were supposed to run. The loader builds ONLY the requested half (step 2 loads every snapshot row + head drift + the shop name), which is why switching steps is a navigation and not local state. `/app/seo/onpage` remains as a redirect carrying its `?tab=` across, for bookmarks and the dashboard's deep links. Step 2's loading lives in [onpage-report.server.ts](app/services/seo/onpage-report.server.ts), its rendering in [OnPageReportView.tsx](app/components/seo/crawl/OnPageReportView.tsx) (tiles and sections separately, because they land in different cards). The page order is fixed: **explanation → scan → step badges → results**. `CrawlSnapshotHeader` is the SCAN card — the run button, the run's own warnings, and controls that change what the crawl DOES (the external-link opt-in) — and nothing else; the result tiles sit in their own card BELOW the two `StepTile`s, since they belong to whichever step is open. With the tiles inside the scan card the page read "here is the scan, here are ITS numbers, and now, afterwards, here is which of two reports you were looking at". The crawl diff is a RESULT too, so it sits directly above the result tiles, not above the scan card. Both halves read the SAME snapshot through `loadLatestSnapshot` ([crawl-snapshot.server.ts](app/services/seo/crawl-snapshot.server.ts)); never add a second single-flight query or a second header. Report primitives live in [components/seo/crawl/](app/components/seo/crawl/), not route-local.
- **A translated resource is served under a TRANSLATED handle.** `/es/products/caja-kumiko-…` and `/products/kumikobox-…` are one product, and the content cache only stores the primary handle — so `resolvePathsToResources` ([url-resolver.server.ts](app/services/seo/url-resolver.server.ts)) falls back to `ContentTranslation` (`key: "handle"`) for the handles the primary lookup missed. Without it every foreign-locale URL of a translating shop resolves to `id: null`, which on the crawl report means no "open in editor" on most of the catalogue. Shopify ALSO answers 200 for the primary handle behind a locale prefix (`/es/products/<german-handle>`), serving the untranslated `<title>` and canonicalising to the translated URL — which is why duplicate detection runs only over `selfCanonicalPages`: a page whose canonical points elsewhere is not indexed under its own URL and cannot be half of a duplicate-content finding. Skipping that reported one product as five duplicates on every multilingual shop.

- **Every path rule must survive a locale prefix.** Shopify serves each storefront path under every published locale, so a rule anchored at `/cart` or `/policies` silently applies to the primary locale only. `stripLocalePrefix` / `localeVariants` ([locale-path.shared.ts](app/services/seo/locale-path.shared.ts)) is THE stripping rule — the crawl denylist, `expectedNoindexReason` and `hasEditableMetadata` all test against the raw path AND the stripped one (an additional match, never a replacement, so `/de/cart-bags` stays allowed). The denylist matching only the raw path is how `/it/cart`, `/es/account` and `/fr/checkout` got crawled — including the PII-adjacent ones the denylist exists for — and then reported as on-page findings.
- **Some pages have no metadata surface AT ALL, and reporting them is not a finding.** `shopPolicyUpdate` takes `{ type, body }` — there is no `seo` input and no metafield, so every `/policies/*` page of every shop is served without a meta description, by construction. `/collections/all` is Shopify's reserved virtual listing, not a Collection record (`all` cannot be taken as a handle), and a paginated `?page=N` URL carries page 1's metadata. `hasEditableMetadata` ([onpage.service.ts](app/services/seo/onpage.service.ts)) is the one predicate; the missing-description list, both duplicate groupings and the CSV export share it, and the excluded count is SHOWN (`metadataSkipped`), never silently dropped. Without it a five-locale shop's whole meta-description category was pages nobody can fix, and `?page=2` vs `?page=3` of one listing reported each other as duplicate content. `?page=1` is a separate matter: it is the same document as the bare URL, so `normalizeCrawlUrl` drops it rather than crawling the page twice.
- **A policy page is a deep-link target but not an `AuditType`.** `/policies/refund-policy` resolves to a real `ShopPolicy` (its handle IS the type in kebab case — the record has no handle column), so the crawl report can offer "open in editor" into `/app/policies?select=<gid>`. It is NOT part of the audit: no SEO title, no meta description, no coverage score. `DeepLinkType` / `isAuditType` ([resource-types.shared.ts](app/services/seo/resource-types.shared.ts)) are the split — every `Record<AuditType, …>` map (dashboard buckets, "Fix with AI", head drift) narrows with `isAuditType`, and the report UI uses the wider type. The vocabulary lives in its own module because `crawl.service.ts` needs `isAuditType` as a value and `audit.service.ts` already imports crawl.service.
- **`noindex` overlaps the sitemap section, and the overlap is the point.** The sitemap tab decides which pages SHOULD be excluded; the on-page step reports which ones ARE excluded without anyone asking. `loadExpectedNoindexReasons` (crawl-snapshot.server.ts) is the one place that knows what counts as deliberate: APPLIED (never merely suggested) `SeoSitemapExclusion` rows, and UNLISTED products — Shopify serves those with `noindex,nofollow` itself (documented and measured, see [sitemap.service.ts](app/services/seo/sitemap.service.ts)), so without that entry every unlisted product tops the report and the dashboard as a critical, unexplained exclusion.
- **A robots directive can carry a VALUE.** `max-image-preview:none`, `max-snippet:`, `max-video-preview:` and `unavailable_after:` are valid and common; taking "everything after the colon" as the token (which is right for a `googlebot:` user-agent prefix) reduces the first to the bare word `none` — shorthand for `noindex,nofollow`. That put perfectly indexable pages at the top of the dashboard. `robotsTokens`/`deriveIndexability` live in [indexability.shared.ts](app/services/seo/indexability.shared.ts) and ONLY there: `crawl-diff.ts` needs the same rule in component scope and its hand-copied duplicate is how that bug shipped twice.

- **An empty crawl column is never evidence.** `SeoCrawlPage.metaRobots == ""` means "nothing served" OR "row written before the column existed" — indistinguishable, exactly like the `translatableContent`/`jsonLdTypes` traps. `indexabilityKnown` is the discriminator and is set ONLY when a body was actually parsed. Consequences that are load-bearing: pre-existing columns (`title`, `metaDesc`, `canonical`, `h1Count`, `wordCount`) hold real values on old snapshots and are judged on 2xx alone (`judgeable` in [onpage.service.ts](app/services/seo/onpage.service.ts) falls back when NO row knows); rules built on the NEW columns (`h1First`, `imgMissingAlt`) must render "unknown", never "none found"; and `diffCrawls` hides the indexability half unless BOTH snapshots know, or the first crawl after a deploy reports the whole catalogue as changed. Never read an empty column as "fine".
- **Activation is the LAST step of a markup section, never the first — and a switch is judged against what the storefront serves.** `/app/seo/structured-data` used to put the two embed buttons above its own measurement, i.e. in the order in which the merchant makes the mistake before they can see it: on a live shop that produced 12 invalid items in the Rich Results Test, because the product block uses Dawn's `@id` scheme deliberately (it is meant to REPLACE the theme's schema, not join it) so Google MERGES the two nodes and every field both sides deliver lands twice. `activationGate` ([markup-activation.shared.ts](app/services/seo/markup-activation.shared.ts), pure and IMPORT-FREE — the section renders `JSON_LD_SWITCHES` and `APP_SOCIAL_TAGS` in component scope, so a single import of an audit service there pulls `crawl-markup-rows.server.ts` into the client bundle and `npm run build` refuses it, which typecheck and vitest both miss) is the one place that turns a crawl into "may this switch go on", and four of its nine verdicts exist because collapsing them produces a confident wrong answer. **A missing measurement is never a green light** — no crawl, no parsed body, or an empty column all yield `unknown`, the same rule as `indexabilityKnown` / `attributesSyncedAt`. **"Switch ours off" is only advice where one copy is provably ours** (`appIsOneCopy`); where the duplication is between the theme and other apps, our switch changes nothing. **Markup that carries no marker is attributed to a FOREIGN source — the theme OR another app — by decision and not by evidence** (`UNMARKED_COUNTS_AS_FOREIGN`; the action bucket is `foreignFix`, never `themeFix`, because naming the theme sends a merchant to the one place the markup may not be): the absence has two causes the data cannot separate — a crawl older than the `data-contentpilot` marker, or our embed being OFF, in which case no page can carry the marker and no re-crawl resolves it — and with a days-old marker and almost no installs the owner judged "origin unknown" the worse default, since it was the state nearly every merchant would see. It cannot cause double markup (under BOTH causes the type is already on the page, so "do not switch on" holds either way); only the attribution can be wrong, which the section admits in one line whenever no marker was seen. The hedge verdict stays in the type and the gate so restoring it is one constant, and it is retired outright the day the marker's release date is a known fact — a crawl newer than that which found no marker PROVES the embed is off. And **a REPEATABLE type gets no verdict at all**: three product videos are three `VideoObject`s, the duplicate rule is correctly silent there, so a 0 means "not checked". The stats are bucketed per (canonical type, crawl `resourceType`) and each `MarkupSwitch` declares the `scopes` its Liquid guard emits on — judging shop-wide told merchants their theme's `FAQPage` on `/pages/faq` collided with ours on product pages, two markups that never meet.
- **Open Graph is measured exactly like JSON-LD, off the same snapshot read.** `SeoCrawlPage.ogTags`/`twitterTags`/`ogAppTags` keep REPEATS (two `og:image` on one page are for Facebook and LinkedIn what two `Product` nodes are for Google), `socialKnown` is their discriminator, and `social-meta.liquid` carries `data-contentpilot="og"` on every tag so "which copy is ours" is answerable at all. `extractSocialTags` reads BOTH attribute spellings and buckets by NAMESPACE — OG is defined on `property=` and Twitter on `name=` but themes mix them constantly, and keying off the attribute reports a served tag as missing over a spelling nobody notices. [crawl-markup-rows.server.ts](app/services/seo/crawl-markup-rows.server.ts) is the ONE read behind both halves: two `findFirst` calls could land on different snapshots the moment a crawl finishes between them, and it also owns the judged-rows rule (`runCrawl` persists a row for every URL it touched but fills the markup columns only where it parsed a body). Deliberately absent: a catalog-side social audit — what can reach `og:title`/`og:image` is the SEO title, meta description and product image, which `analyzeStore` and the JSON-LD batch already score.
- **Every on-page category is filtered against its own false positives.** A `noindex` is often deliberate (`EXPECTED_NOINDEX_PATTERNS` + APPLIED — never merely suggested — `SeoSitemapExclusion` rows). Shopify canonicalises `/collections/x/products/y` → `/products/y` correctly, so only demonstrable canonical defects are reported and a canonical whose target was never crawled yields nothing. Thin content is a percentile WITHIN a `resourceType` (`countWords` keeps header/aside/theme boilerplate, so an absolute threshold is meaningless), with types under 20 pages skipped AND said so. `alt=""` counts as missing, which is why that category says "without alt text", never "error". These filters are the feature — dropping one turns the tab into noise.
- **The canonical host comes from the crawled URLs, never from a lookup.** `fetchPrimaryDomain` falls back to the myshopify host when the Admin call is throttled, while every crawled URL is normalized to the PRIMARY domain — one bad lookup would flag every page as a critical "canonical points at a foreign domain". `canonicalHostFromPages` ([onpage.service.ts](app/services/seo/onpage.service.ts)) is the resolver; the looked-up domain goes in as an alias only.
- **External-link checking is a SECOND pass with its own regime, after the crawl is persisted.** [external-links.ts](app/services/seo/external-links.ts): 6 parallel but max 2 per host (Shopify's shield does not apply to strangers; manners toward one host still do), HEAD then a one-byte GET on 403/405/501 (a huge share of hosts refuse HEAD while serving fine — without the fallback the report calls healthy links dead), dedup by the FULL url including query, and `isPrivateOrLoopbackHost` re-checked on EVERY redirect hop. 403/429 is a bot shield, NOT a dead link — the same rule as `isBotBlockStatus` internally. A hard 120s budget with the task heartbeat wired through it, and everything it did not reach is persisted as `EXTERNAL_NOT_CHECKED` rather than dropped: a missing row is indistinguishable from a healthy one. The pass must never be able to downgrade a persisted crawl to "failed". Opt-out on `AISettings.seoCrawlExternalLinks` (default on); with it off the UI shows "—", never 0.
- **Redirect chains need no crawl.** `A → B → C` is fully derivable from Shopify's own redirect list ([redirect-chains.ts](app/services/seo/redirect-chains.ts), pure + client-safe). Paths match case-insensitively and slash-normalized (Shopify does too); an absolute target on the primary host is followed, a foreign host ends the chain, and with no known primary host every absolute target ends it — a missed finding, never a wrong fix. A loop gets no auto-fix (there is no end target to choose) and each cycle is reported once, not once per member. Resolving repoints only the FIRST redirect and re-derives the chain server-side; intermediates stay (they can carry their own inbound links) and the UI must say so.
- **Crawl/on-page CSV exports are resource routes and gate themselves.** Directly GET-reachable, so `meetsPlan(plan, "pro")` lives in the route — same class as the `/api/ai` handlers. No row cap (UI_ROW_CAP is a rendering limit; getting past it is why merchants export). One serializer, [csv-export.ts](app/services/seo/csv-export.ts): `;` + BOM for the new exports (Excel DE), and a formula-injection guard because these files carry `<title>` text and URLs this app did not author.
- **Stock is money, so the echo rule is stricter and the arithmetic is forbidden.** Phase 4 MIRRORS inventory into `InventoryLevel` / `Location` / `ProductPublication`, but nothing reads those rows to render the panel: quantities move from orders, returns and other apps between two page loads, so the panel reads Shopify LIVE and a failed load says so rather than showing a stale number. `inventorySetQuantities` takes an ABSOLUTE quantity and [commerce-write.server.ts](app/services/commerce-write.server.ts) always pairs it with `compareQuantity` (`ignoreCompareQuantity: false`), so a value that moved under the merchant's feet is REFUSED (`stockChangedMeanwhile`) rather than overwritten; computing `cached + delta` is the classic source of inventory drift and this module deliberately offers nothing to compute it with. A write counts as successful only when Shopify echoes the new quantity back AND it matches, per change — `userErrors: []` is not enough, and a partial apply mirrors only its confirmed half. Only `on_hand` is writable: `available` is DERIVED (on hand minus open commitments) and writing it would contradict them. **Untracked is not zero** — `tracked: false` means Shopify keeps no count, `null` means never synced, and rendering either as 0 tells a merchant they are sold out of something they can sell without limit. `commerceSyncedAt` is that block's discriminator, exactly like `attributesSyncedAt`; `variantCommerceColumns` returns `{}` for a response that did not carry the block so a narrower query can neither overwrite nor stamp knowledge. Stock lives on its OWN route ([api.product-commerce.tsx](app/routes/api.product-commerce.tsx), plan-gated in the route) and keeps its own state — a volatile number in the editor's flat value map would be stale by the time anyone pressed save. What it no longer keeps is its own BUTTON: it registers `{hasChanges, save}` through [CommerceSaveContext](app/contexts/CommerceSaveContext.tsx) and the editor's one save bar drives it alongside the content and sub-resource saves. Two save buttons on one screen is a question the merchant has to answer ("did that one include my text?") and the answer was no. The registration effect sits ABOVE the panel's early returns — a hook below them changes the hook count between renders and drops the whole editor into its error boundary, which this component shipped once. Shopify reports an inventory LEVEL only where an item is ACTIVATED at a location, so a shop's other locations are absent rather than zero: the panel lists them from a separate per-shop `locations` query as "not stocked here" with an echo-verified `inventoryActivate` as the way in — absent read as "you have one warehouse" is what made a merchant think the panel was broken.
- **`status: ACTIVE` is not visibility, and `ProductPublication` is what finally says so.** A product published to no sales channel is invisible everywhere and the Shopify admin does not mention it on the product page either. An empty publication list is therefore a MEANINGFUL state, which is why `productPublicationRows` returns `null` for a response that did not carry the block rather than an empty list: wiping on a partial response would manufacture exactly the alarming state the feature exists to reveal. Shopify's own `isPublished` is taken verbatim (it already accounts for a future publish date) — recomputing it from the date is a second answer to one question, and the two drift.
- **A rule-based collection is untouchable in BOTH directions, and "unknown" counts as rule-based.** Leaving a smart collection is undone by its rule within seconds; JOINING one is refused by Shopify, and because `productUpdate` is atomic that refusal takes the merchant's title, description and SEO edits with it. `Collection.isSmart` is `NOT NULL DEFAULT false` on a column added to an existing table, so `attributesSyncedAt` gates every read of it — an unsynced row is UNKNOWN, and `diffCollectionMembership` refuses unknown as well as known-automated, because not adding a membership costs a click while adding one wrongly costs a text edit. Membership is a JOIN/LEAVE diff whose BEFORE side is the cache; the picker UNIONS the shop's collections with the product's own memberships, since a membership it cannot show is one it would silently remove.
- **A `#graphql` document carries no comments and no non-ASCII — the text between the backticks is sent to Shopify verbatim.** Three explanatory lines added to the blog loader's `getBlogs` query took `/app/blog` down with `syntax error, unexpected invalid token ("\\") at [11, 3]` — line 11 was the comment's last line, and there is no backslash anywhere in the document. It is NOT reproducible locally: the exact bytes the client puts on the wire (verified by capturing `customFetchApi`'s body) parse cleanly under graphql-js AND under `graphql-c_parser`, the parser whose error format Shopify emits — so the mangling happens on Shopify's ingest path and the reported position is garbage. Every comment this repo ever put inside a document carried a `§` or `—`, which is why the rule bans both: prose and non-ASCII. Neither costs anything outside the backticks — put the explanation in a `//` comment next to the template (it can then say whatever it likes, backticks included, which retires the older TS1005 trap where a `` ` `` inside a `#` comment ended the template literal mid-query and cost four debugging rounds). Search values with accents ride in `variables`, never inline. [graphql-document-hygiene.test.ts](tests/unit/graphql-document-hygiene.test.ts) enforces both halves over every `#graphql` literal in the repo, walking `${…}` interpolation by hand so a nested template cannot hide the rest of a document from the scan.
- **One field→translation-key map.** `FIELD_TO_TRANSLATION_KEY` / `fieldTranslationKeyMap(resourceType)` in [shopify-content.service.ts](src/services/shopify-content.service.ts) is THE map (ShopPolicy translates `body`→`body`; every other type maps `body`/`description`→`body_html`, `seoTitle`→`meta_title`, `metaDescription`→`meta_description`, `productType`→`product_type`, `summary`→`summary_html`). Never re-declare it — historic copies drifted. `TranslatableResourceType` enum is `PAGE`/`ARTICLE`/`BLOG`/`COLLECTION` (the `ONLINE_STORE_*` names were removed with 2024-10).

## Deploy-critical gotchas

- **A video's `uploadDate` cannot come from Liquid, so the sync carries it.** `VideoObject` is emitted by the storefront block from the native `product.media`, which has everything Google requires EXCEPT the upload date — Liquid's media objects carry no creation date, and guessing one is the `priceValidUntil` fabrication all over again. The Admin API has it (`Video`/`ExternalVideo` implement `File.createdAt`), so the product sync selects it through the shared `PRODUCT_VIDEO_MEDIA_FIELDS` and [video-schema.server.ts](app/services/seo/video-schema.server.ts) writes a `{numeric media id: full ISO-8601 timestamp}` map into the `custom.video_upload_dates` metafield the block reads back. Five things are load-bearing. The value keeps its TIME and its ZONE: Google rejects a date-only `uploadDate` ("invalid date/time value" plus "missing timezone", measured 2026-08-18 in the Rich Results Test on a live shop), and `File.createdAt` carries both — the first cut truncated to `YYYY-MM-DD` and threw away exactly what Google asks for. The merchant override is the one place with no time to keep: `custom.video_upload_date` is a `date` metafield, so the block appends `T12:00:00Z` — midday UTC is the only stamp that lands on the stated day in every real timezone, where midnight would read as the previous day west of Greenwich and misreport a date a person set by hand. The key is the NUMERIC id: Liquid's `media.id` is a number, so a GID-keyed map could never be looked up on the storefront (and the block coerces with `| append: ''`, because JSON keys are strings). The write is DIFF-driven against `Product.videoSchemaJson`, a mirror of what was last PUSHED and echoed — an unchanged catalog costs zero Shopify calls, and a silent no-op must never mark a product as done. "No videos" is `null`, i.e. `metafieldsDelete`, never `{}` — `metafieldsSet` rejects an empty value. And only the THREE product queries with the full `media(first: 250)` window feed it: `api.sync-missing-products` selects 20 and cannot tell "no videos" from "outside the window", so a map built there would drop a real video's date (the same narrower-response rule the attribute block follows). The merchant's own `custom.video_upload_date` still wins per product — they may know the true first publication, and a person's stated fact outranks a derived one. One rail keeps the write from feeding itself, and it is the DIFF, not a flag: our own metafield write fires `products/update`, but the mirror has already advanced and the product upsert never assigns `videoSchemaJson`, so the echo run writes nothing and the sequence ends after one extra pass. Suppressing the write on the webhook path (`writeVideoSchema: false`, the first cut) bought nothing and cost the case the feature exists for — a merchant who adds a video in the admin fires ONLY that webhook, so their product had no `uploadDate` until the next full sync. Confirmation is by OWNER id from the mutation echo with the payload's PRESENCE as the proof — a throttled `data: null` carries an empty `userErrors` too, and treating that as success would advance the mirror past a write that never happened. Failure is per ENTRY, never per batch: `failedBatchIndices` reads the entry index out of Shopify's `field` path, so one stale product id among 25 no longer strands the other 24 (they would be retried on every sync forever), and an owner whose metafield was ALREADY gone counts as cleared unless an error names it — checking the echo list's emptiness instead left every already-clean product in a mixed batch unconfirmed. An error that cannot be attributed to an index confirms only what was explicitly echoed. Adding the video fragment also made "has an id" stop meaning "is an image": `imageMediaNodes` in [product-sync.service.ts](app/services/product-sync.service.ts) is the guard every image path now goes through, or videos end up as `ProductImage` rows and in the alt-text translation queries.
- **A gallery video is found by a LIVE sweep, and its date can only come from the merchant.** A video that lives only in a variant gallery (`custom.variant_gallery_order` entries with `kind: "url"`, or `custom.variant_external_videos`) has no `File` behind it, so `File.createdAt` — and with it the whole `custom.video_upload_dates` map the sync writes — cannot apply; without `custom.video_upload_date` the block omits `uploadDate` rather than inventing one, and Google's video rich result never fires. [gallery-video-audit.server.ts](app/services/seo/gallery-video-audit.server.ts) is what makes that visible. It sweeps LIVE because nothing mirrors those metafields (`ProductVariant.galleryJson` holds file GIDs, so a URL leaves no trace), flat over `productVariants` and never nested inside `products` (a nested connection multiplies the query cost by the parent's page size and throttles any real catalogue), and it rides on the EXISTING `seoJsonLdAudit` button rather than growing a second task type — which is also why the sweep lives in the handler and not in `json-ld-audit.service.ts`, whose "DB-cache-only, testable without mocking admin.graphql" contract stays true. Two counts that must never be merged: a YouTube video without a date is one metafield from a rich result, while a VIMEO gallery video emits nothing at all (the rich result needs a thumbnail and none can be derived from a Vimeo link), so a date would change nothing. And three not-checked states, none of which may render as "none found": a task result from before the key existed, a sweep that threw, and a sweep refused BEFORE it read one variant — that last zero would have been a confident false negative from a query that never ran. It also SUBTRACTS the product's own external-video media before counting, because the block seeds its dedup set from them: a video that is both product media and a gallery link is emitted once, from the media loop, WITH the automatic date — and reporting it as dateless pushes the merchant to set `custom.video_upload_date`, the product-WIDE override, which replaces the accurate `File.createdAt` stamp of every media video on that product with one guessed date. The block's 5-emitted-videos cap is modelled for the same reason, DRAFT/ARCHIVED products are skipped (`catalog-readiness`'s rule), and the sweep retries `THROTTLED` — Shopify reports it as HTTP 200 with an `errors` entry the transport does not retry, so without that the answer on any shop large enough to have galleries is "we did not look". **There is exactly ONE TypeScript parser for these URLs and it is `parseExternalVideoUrl` in [mediaKind.ts](app/utils/mediaKind.ts)** — the parser that decides what is ever WRITTEN into those metafields, so the audit reads back with the parser that wrote; a second copy was added here and removed again, because that is how this parser drifted before (three copies, two of which had lost `youtube.com/shorts/`). [external-video-parser-parity.test.ts](tests/unit/external-video-parser-parity.test.ts) pins it against the snippet's branch set. Liquid's `split` is Ruby's and DROPS trailing empty strings, which is why `"https://youtu.be/" | split: 'youtu.be/' | last` is `"https://"` and the snippet used to answer `youtube|https:` — the id guard against `:` and `.` is load-bearing, not defensive.
- **The bulk-assignment filename convention lives until the upload, and not one step further.** `parseFilenames.ts` reads `ProductName_Variant1_..._Identifier.ext` at DROP time and writes the result into the variant's gallery / image key; nothing reads it again for the ASSIGNMENT. So an SEO rename does not break the bulk assignment — the two only collide if a rename happens BEFORE the parse. One other reader exists and is easy to miss: [image-alt-match.ts](app/services/seo/image-alt-match.ts) maps a crawl's accessibility findings onto `ProductImage` rows by the normalized filename STEM, so a mass rename would silently drop the "fix this alt text" link until the next product sync re-caches the URLs. Noted because the opposite was assumed once: if filename SEO is ever built, the interesting half is naming at upload (the app already owns that moment via the staged upload + WebP step, and the file is referenced nowhere yet), with parsing strictly first; a later mass rename is possible through `fileUpdate` (Shopify keeps references by file id) but changes every CDN URL, which is why it would have to be a deliberate, announced action rather than an automatic sweep.
- **The app never edits the merchant's theme CODE.** Product decision (2026-08-18): no injecting markup into a merchant's templates or sections, no performance surgery (lazy-load, CSS/JS minify), no autopilot that rewrites theme files it did not create. Page speed stays a DIAGNOSIS in this app (PageSpeed Insights + real-user samples), never a repair — which is also why the competitor feature "speed optimization" is a stated non-goal rather than a backlog item. The boundary is ownership, not the file type: app-OWNED theme files are fine and already shipped (`templates/llms.txt.liquid`, `templates/agents.md.liquid`, the managed `templates/robots.txt.liquid`, theme content translations) because each one is a file the app created, can hand back, and that leaves the merchant's own code untouched.
- **Only ONE theme app extension per Shopify app.** All storefront/theme blocks (JSON-LD, social-meta, app embeds) MUST live under [extensions/storefront/](extensions/storefront/). Creating a second `type = "theme"` extension silently breaks `shopify app deploy`.
- **The extension has a hard 100 KiB (102400 bytes) Liquid budget.** Every `extensions/storefront/blocks/*.liquid` counts together; `assets/` does not (served statically — that's why the block logic lives there). Over budget, the CLI fails with `bundle: Extension Liquid content size exceeds 100 KB limit`. The commented sources are already over it, so deploy via `npm run deploy` ([scripts/deploy-minified.mjs](scripts/deploy-minified.mjs)) — it minifies the blocks in place, deploys, and restores the sources in a `finally` (also on failure/Ctrl-C). **Never commit minified blocks**; `blocks/` stays commented in git. Minification skips `<script>`/`<style>`/`<pre>`/`<textarea>`/`{% raw %}` and every `{% … %}` / `{{ … }}` interior byte-identically, so comments inside a JSON island buy no headroom — when it gets tight, move markup into `assets/`. Check with `npm run minify:blocks`.
- **Never add a `postdeploy` script to package.json.** npm auto-runs `pre<x>`/`post<x>` around every script, so a `postdeploy` entry fires after each `npm run deploy` — *after* the extension version is already released. It used to run [scripts/migrate-baseline.js](scripts/migrate-baseline.js) (a DB migration, unrelated to the Shopify deploy) and turned successful releases into a red exit code, inviting a retry that publishes a second version. Railway never called it: it starts via `npm run start:production` → `run-all-migrations.js`. That start command comes from [railway.json](railway.json) — every Railway service here builds with the `Dockerfile`, whose `CMD` (`npm run start` — no migrations) the config file overrides. A `Procfile` and a `nixpacks.toml` used to sit alongside it describing a build path Railway never takes; both were deleted rather than left as a second, contradicting answer. Deploy mechanics live in `railway.json` / `railway.dbalert.json` — see [RAILWAY-SETUP.md](RAILWAY-SETUP.md) §0 for which file belongs to which service and what can only live in the dashboard. Run the baseline migration explicitly with `npm run prisma:migrate`.
- **The DB backup is a fourth Railway service, and its dump is verified before it counts.** [db-backup.mjs](scripts/db-backup.mjs) (config in [railway.dbbackup.json](railway.dbbackup.json), env table in [RAILWAY-SETUP.md](RAILWAY-SETUP.md) §0) dumps to Cloudflare R2 nightly. Three rules are load-bearing: `pg_dump` must be **>= the server major** or it refuses the dump — an unknown version on either side counts as incompatible, never as fine, and the Dockerfile's unversioned `postgresql-client` is what gets pinned when Railway's Postgres moves; the dump is fed back through `pg_restore --list` before upload, because a truncated archive is otherwise indistinguishable from a small database until the restore you attempt under pressure; and retention never deletes the newest `BACKUP_KEEP_MINIMUM` dumps regardless of age, so a cron that silently stopped cannot have "everything is old" read as "delete everything". `DATABASE_URL` is expanded into `PG*` env vars rather than passed as argv — a connection string on the command line is readable from `/proc` by anything else in the container.
- **App embeds cannot inject `<head>` CSS.** `{% stylesheet %}` is not available in app blocks; styles must live inline or in a section/block that participates in the theme's asset pipeline.
- **Meta title/description on pages, blogs, articles ≠ native `seo` field.** They live in `global.title_tag` / `description_tag` **metafields**. Clearing requires `metafieldsDelete` — setting an empty string does NOT clear.
- **`metafieldsSet` with `""` is rejected** ("Value can't be blank") — clear a metafield via `metafieldsDelete` (`MetafieldIdentifierInput`: `ownerId`+`namespace`+`key`; the old GID-based `metafieldDelete` was removed 2025-01). Always send `type` on `metafieldsSet` (required when creating without a definition); max 25 per call, atomic upsert.
- **`write_metaobject_definitions` was added to BOTH TOMLs (2026-08) so a metaobject TYPE can be deleted — the fourth scope change, and it costs a re-consent round like every other.** Deleting a definition is the most destructive call in this codebase: Shopify removes every ENTRY of that type with it, and neither asks about them nor reports how many it removed. That cascade is Shopify's documented behaviour and is **NOT measured here** — it is stated as a WARNING in the dialog, never as a measurement, and whether a STANDARD definition can be deleted at all is likewise unmeasured (its `userError` travels back verbatim). So the confirmation names the count from THIS APP's cache and says it is the app's number, `metaobjectDefinition` is its OWN `DeletableResource` (reusing `metaobject` is exactly how the page once grew a Delete that 400ed on a `metaobject_type_<type>` pseudo id, which is not a Shopify object at all), and the cache purge reads the entry ids BEFORE deleting them — `MetaobjectTranslation` is keyed by `metaobjectId`, not by the definition, so a delete-first order strands its rows forever. The echo rule is unchanged: `deletedId`, not `userErrors: []` — but the PURGE that follows it may no longer report the delete as failed: it is bookkeeping after an irreversible act, and answering "could not delete" sent the merchant into a retry that then said "nothing was removed locally" about an object that no longer existed. A stale cache self-heals on the next sync; a false failure does not. The count in the confirmation comes from the TYPE ROW of the page loader, never from the entry loader — `loaded.contentCount` is the SEARCH-FILTERED count, so a merchant who had typed into the entry search would have been offered "3 entries" for a type holding sixty. And a KNOWN in-use entry refuses the whole delete, the same rule and the same reason as the per-entry path. `deleteContent` also gates on the plan in the action: `handleUnifiedContentActions` applies none, and this is directly POST-reachable. The button lives in the action bar and is supplied by the ROUTE (`containerAction`), because only the route holds the definition's real GID.
- **Phase 4 added `write_inventory,read_locations,write_publications` to BOTH TOMLs — the second scope change this app has made.** Each one forces a one-time re-consent of every installed merchant, which is why the rule is that all new scopes ship in ONE deploy: two re-consent rounds in a row is what loses merchants. `read_inventory`/`read_publications` are deliberately NOT requested — a `write_*` scope normally grants the read, and every superfluous scope is a point in the App Store review. An in-app banner explaining the re-consent was built and then removed as unwanted — do not reintroduce one without asking. `AISettings.commerceNoticeDismissedAt` is its leftover column, unused and kept only because dropping a possibly-applied migration is the riskier error.
- **Alt-text writes: `productUpdateMedia` for PRODUCT media, `fileUpdate` for every other image.** The app now declares `read_files,write_files` (added for the bulk editor's image rows — the scope change forced a one-time re-consent of every installed merchant; do not add scopes casually). `productUpdateMedia` is product-scoped and cannot address images outside the catalogue, which is what `fileUpdate` is for; product media deliberately keep the deprecated-but-tested `productUpdateMedia`, the same call the single editor makes. Both go through the echo rule (`writeMediaAltText` / `writeFileAltText` in apply.server.ts). Mirror to DB with `altTextModifiedAt: new Date()` so the self-triggered `products/update` webhook (5-min preserve window) doesn't overwrite the fresh value.
- **Variant pricing is synced in the regular product sync** (`price`/`compareAtPrice`/`barcode` on `ProductVariant`; before this, variant rows only appeared after opening the image manager). The variant upsert must NOT `deleteMany`+recreate — `galleryJson`/`imageKey` come from the image manager; upsert on `id` and delete only ids Shopify no longer returns. Products with >100 variants are flagged `hasMoreVariants` (remainder uncached, editable in the Shopify admin).
- **Partial SEO saves clobber the untouched half.** Sending `seo: { title }` alone on products/collections wipes the primary meta description. Always send both halves or preserve the untouched value.
- **Markets: gate on `status === 'ACTIVE'`, not deprecated `enabled`.** Secondary markets often have `webPresences: []` and share the primary web presence. Do not require web-presence locales to enumerate a market.
- **Theme keys need explicit filename routing on primary save.** In `templates-update.action.ts`, `resolveFilename` maps resource types to theme file names:
  - `ONLINE_STORE_THEME_LOCALE_CONTENT` + `ONLINE_STORE_THEME` → `locales/<primaryLocale>.default.json` (Shopify lowercases regional codes: `pt-BR` → `pt-br`; resolve robustly, do not hardcode)
  - `ONLINE_STORE_THEME_SETTINGS_DATA_SECTIONS` + `ONLINE_STORE_THEME_SETTINGS_CATEGORY` → `config/settings_data.json` (values live under `current.*`)
  - Unmapped resource types silently drop from the Shopify push while still writing the DB — that's a false-success bug pattern.
- **Autofix-normalized richtext: mirror the PUSHED value to DB, not the raw one.** If autofix rewrites a richtext value (`test<p></p>` → `<p>test</p>`) before writing `config/settings_data.json`, STEP 2b of the update handler must mirror the normalized value into `ContentTranslation`. Mirroring the raw value diverges DB from file → next save can't find the old value → save appears to no-op.

## Layout widths — every page and column spends a token, none invents a number

How wide a page or a column is is app-wide state, not a per-route decision: surfaces of the same kind that disagree by a few hundred pixels make the app look like it was assembled from parts, and "make the SEO pages 10% wider" turns into a hunt through routes. Every width lives ONCE, in the `:root` block of [responsive.css](app/styles/responsive.css) next to `--app-page-padding` — the same single-source pattern that variable already established. **No route, component or stylesheet hardcodes a page or column width.**

**Page width** — pick one of three classes for the route's outermost content wrapper:

- `.app-page-width` (`--app-page-width-content`) — reading-width pages: prose, forms, report tables. SEO sections ([app.seo.tsx](app/routes/app.seo.tsx)) and Tasks ([app.tasks.tsx](app/routes/app.tasks.tsx)) use it, deliberately at the same width.
- `.app-page-width-narrow` (`--app-page-width-narrow`) — focused single-task pages that are mostly one list of checkboxes or fields ([app.bulk_.translate.tsx](app/routes/app.bulk_.translate.tsx)).
- `.app-page-width-full` (`--app-page-width-full`, currently `none`) — data grids that turn every extra pixel into column width ([app.bulk.tsx](app/routes/app.bulk.tsx): `BulkGrid` gives uncapped columns `1fr`, so any margin is width thrown away), and sidebar+content layouts that are not reading-width content ([app.settings.tsx](app/routes/app.settings.tsx)). Stated explicitly rather than left off, so "uncapped" reads as a decision.
- `.app-page-width-start` (`--app-page-width-with-list`) — the same reading width as `.app-page-width` **for the content column**, left-aligned instead of centred: for pages whose LEFT edge is a fixed item column that has to stay flush with the window gutter, so only the right edge may be capped. That is every **content page without the item sidebar** (the panel carrying the SEO-score tab): with the sidebar the editor is a three-column workbench that spends the full width, without it nothing stops the middle column from growing across a 4K screen. `UnifiedContentEditor` picks the class off `config.showItemSidebar` (never off `hasSidebar`, which also drops when no item is selected — the page would change width on selection), `ThemeContentDomainPage` mirrors the same choice onto the banners it stacks above the editor, and the two content pages with their own layout ([app.menus.tsx](app/routes/app.menus.tsx), [app.direct-translations.tsx](app/routes/app.direct-translations.tsx)) carry it directly. The token is DERIVED, never a second number: item column + gap + `--app-page-width-content` + the frame's two gutters, which is why those pages spend `var(--app-page-padding)` as their column gap — capping them at the bare reading width instead would spend a third of it on the list and leave the editor narrower than any SEO page.

**Column width** — spent as `width: var(--…)` in the component's inline style (the way `--app-page-padding` is already used):

- `--app-list-column-width` — every "pick an item" column: the item list on the content pages and direct translations ([UnifiedItemList.tsx](app/components/unified/UnifiedItemList.tsx)), the Settings tab nav, the Menus list. They were 330/250/350px; the content list was the one that was right, so it set the token.
- `--app-editor-sidebar-width` + `-min-width` / `-max-width` — the content editor's right-hand SEO/bulk panel. The user drags it, so the token is only the DEFAULT it opens at plus the drag bounds; they live here anyway so the panel can be recycled elsewhere without re-deriving them.

Four mechanics that are easy to get wrong:

- **On a Polaris page the class goes on the `.app-page-content` frame**, alongside it — capping the FRAME keeps its `--app-page-padding` gutter and its inner scroll container (`.app-page-content > *`) intact, while an extra wrapper div would break the single-child scroll rule. `<Page fullWidth>` must stay: without it Polaris' own ~1000px cap wins before ours is reached.
- **The width classes carry no padding on purpose.** `.app-page-content` already owns its gutter, and a second `padding` declaration on the same element would win or lose by rule order. Non-Polaris routes keep their own `padding` in the inline style.
- **A resizable width starts as `null`, not as the number.** [UnifiedContentEditor.tsx](app/components/UnifiedContentEditor.tsx) renders `sidebarWidth ?? "var(--app-editor-sidebar-width)"` and, on the first drag, measures what that rendered as (`getBoundingClientRect`) instead of restating it. Seeding the state with `useState(320)` would put the default in a second place, which is exactly what drifts.
- **The drag bounds are read off the tokens per drag** (`getComputedStyle().getPropertyValue`), and a value that doesn't parse as px drops its half of the clamp rather than becoming `NaN` — `Math.max(NaN, …)` would make the panel unresizable.

## Field chrome — a field looks the same everywhere, and the look lives in one place

The same rule as the widths above, one level down: how an input BOX looks is
app-wide state, not a per-component decision. The product page had two of
everything — the fields inside `.ai-editable-field-wrapper` (title, description,
product type, …) carried a hand-written light-grey border, a semibold label with
a question mark and a "Leeren" button, while every plain Polaris control beside
them (vendor, tags, collections, the category picker) kept Polaris' much darker
default border, a regular-weight label, no help and no way to empty itself. In
one card. **No component states a border colour, a label weight or a clear
button of its own.**

- **The numbers live in the `:root` block of [responsive.css](app/styles/responsive.css)**, next to
  `--app-page-padding` and the widths: `--app-field-border-color`,
  `--app-field-border-radius`, `--app-field-label-weight`, plus the Details
  card's two grid minimums (`--app-attribute-grid-min-width`, `…-compact`).
- **The frame is drawn on Polaris' Backdrop element**, in the one rule in that
  same file — the input itself has `border: none`, and Polaris hardcodes a
  `border-top-color` one shade darker again, so both have to be named.
  Deliberately `.Polaris-TextField__Backdrop` and `.Polaris-Select__Backdrop`
  only: Polaris spends the same `--p-color-input-border` on checkboxes, radio
  buttons and the drop zone, so re-pointing that VARIABLE (the first cut) would
  have lightened every tick box in the app, which is not what "the outline of
  the input boxes" means. Hover and focus stay Polaris': a resting frame is a
  style, a border that darkens under the pointer is an affordance.
  responsive.css loads AFTER Polaris' stylesheet ([app.tsx](app/routes/app.tsx)), so equal
  specificity resolves our way.
- **The SHAPE lives in [FieldChrome.tsx](app/components/unified/FieldChrome.tsx)**: `FieldLabel` (bold, with the
  question mark right after the words) and `FieldClearOverlay` (the Clear button
  in the field's top-right corner, on the label's own line). Every editable
  control goes through both — `AIEditableField`, `AttributeField`,
  `ChipCombobox`, `CollectionsField`, `TaxonomyField`. A label is a `span`, never
  a second `label` element: it is passed INTO the Polaris `label` prop, and a
  nested label is invalid markup that also breaks click-to-focus.
- **The clear button is drawn only where `""` is a value the field can HOLD.** A
  select and a toggle are enums — Shopify stores one of their options, never
  nothing — so a Clear there would either write a value the API rejects at the
  schema level or silently do nothing. `ChipCombobox` clears itself rather than
  handing back an empty list: a LOCKED chip (a rule-based collection membership)
  survives, because a bulk removal of it is the same refused write as removing it
  one chip at a time, and `productUpdate` is atomic — the refusal would take the
  merchant's text edits with it.
- **What a field is FOR belongs in its question mark, not under the box.**
  `helpKeyMap` in [UnifiedFieldRenderer.tsx](app/components/UnifiedFieldRenderer.tsx) is the one map from field key to
  `t.help` entry, and every editable field on a content page names one.
  `HelpTooltip` renders nothing for a key the language bundle does not carry, so
  a key may be named before its text is written and never shows as an empty
  circle. `helpText` under the control is for a value hint that changes with the
  value (a character count), not for an explanation a merchant reads once.
- **A Details section may be HEADLESS.** `HEADLESS_DETAILS_SECTIONS` in
  [details-sections.ts](app/config/details-sections.ts) is the set; "organization" is in it, because the word
  says nothing its own fields (vendor, product type, collections, tags) do not
  already say. A headless section drops the heading AND the subcard and renders
  as one compact grid row — which is why `shouldRenderDetailsSections` must not
  count it: it draws no frame, so counting it would leave a single titled box
  with nothing to be separated from, the box-in-a-box that guard exists to
  prevent. The two grid minimums are the other half: with the wide one only
  three of the four organization fields fitted on a normal screen.

## Single-language shops (one shop locale) — mandatory rules for every new UI

A shop with only its primary locale must never be offered translation UI it cannot use. These rules are not optional polish; apply them to **every new button, bar or section** that touches locales. Reference implementation: [LocaleAvailabilityContext.tsx](app/contexts/LocaleAvailabilityContext.tsx) + [DisabledActionTooltip.tsx](app/components/DisabledActionTooltip.tsx).

- **Locale buttons/bars: REMOVE, don't disable.** Anything that switches between languages (locale chip rows, `UnifiedLanguageBar`, `MobileToolbar`'s locale row, the keyword/glossary/dashboard locale bars) renders nothing at `locales.length <= 1` — a single permanently-active button is noise. Drop the surrounding `<Card>`/wrapper too so no empty box is left: `shouldRenderLanguageBar()` in [UnifiedLanguageBar.tsx](app/components/unified/UnifiedLanguageBar.tsx) is the caller-side twin of the bar's internal emptiness check. Kill the Ctrl+click hint with the bar (the primary locale can't be toggled off).
- **Everything else: DISABLE + tooltip, don't hide.** Translate, translate-to-all-locales, copy-to-all-locales, "Accept & Translate", alt-text translation, per-option/metafield 🌍 — all stay visible, greyed out, with `t.common.requiresSecondLanguage` as the tooltip. Hiding them makes merchants think the feature is missing.
- **Get the flag from the context, not from props.** Inside the editor tree call `useSingleLocaleHint()` — it returns `undefined` when the shop is multi-language (so `disabled={... || !!singleLocaleHint}` and `<DisabledActionTooltip hint={singleLocaleHint}>` are no-ops) and the reason string otherwise. `UnifiedContentEditor` provides `LocaleAvailabilityProvider`; components outside it (image manager panels that receive `shopLocales`/`enabledLanguages` as props) derive the same hint locally.
- **Disabled controls need the wrapper.** Browsers do not dispatch pointer events for a disabled control, so a bare Polaris `<Tooltip>` around it never opens. Always wrap with `DisabledActionTooltip`. In an `ActionList` (no hover tooltip possible) use `disabled` + `helpText` instead.
- **Whole sections that only exist for translation** (e.g. the hreflang audit): mark the descriptor `requiresMultipleLocales` ([seo-sections.ts](app/config/seo-sections.ts)), grey the nav chip with a **🌐** marker (never 🔒 — that reads as "upgrade your plan") and render the explanation in place of the section body. A plan gate outranks the language gate in both the marker and the body.
- **Never gate on a failed lookup.** `getCachedShopLocales` swallows non-401 errors and resolves with `[]`, so an empty list means "lookup failed", not "one locale" — treat it as multi-language. Do not `catch` around it: it re-throws 401 on purpose so the request can re-authenticate.
- **Handlers stay defensive anyway.** The client gate is UI only; every `targetLocales = enabled.filter(l => l !== primaryLocale)` path keeps its `length === 0` guard, and server actions keep returning a successful no-op.
- **Exception — Direct translations.** `/app/direct-translations` targets *all* published locales including the primary (the source string is arbitrary storefront text), so its translate buttons stay enabled with a single locale. Only its locale bar disappears.

## Auth / boundaries

- Shopify auth + session handled by the standard `@shopify/shopify-app-remix` flow.
- Multi-tenant: every DB row is scoped by `shopId`. Translations are additionally scoped by `locale`, and theme content by `themeId` + `marketId`.
- **`ThemeTranslation` unique key includes both `themeId` AND `marketId`.** Accessor: `shop_resourceId_groupId_key_locale_themeId_marketId`. It is the only translation table folding both.

## Working agreement

- **Every larger or system-relevant change ends with a review pass.** Once the rebuild is finished (and typecheck + tests are green), run an independent review agent over the diff — `/code-review high` on the branch, or a subagent with the same brief — and then FIX what it finds before reporting the work as done. "System-relevant" = anything touching a write path, translation/sync logic, auth or plan gating, a shared component or context used across pages, DB schema or migrations, deploy scripts, or a cross-cutting UI rule like the single-language rules above. Small local edits (a string, one styling tweak, a test) don't need it.
- Report the findings and what you did with each; if a finding is a false positive, say why instead of silently dropping it.
