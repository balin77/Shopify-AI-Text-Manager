# CLAUDE.md — Shopify AI Text Manager (ContentPilot)

Curated architectural notes for Claude Code. Public repo — nothing security-sensitive in here.

## Project

Shopify embedded app (Remix + Vite + Prisma + Polaris) for AI content generation, SEO, and multi-locale/market translation of products, collections, pages, blogs, articles, metaobjects, and theme content.

## Stack

- **Remix** (Vite) — see [remix.config.js](remix.config.js), [vite.config.ts](vite.config.ts)
- **Prisma + PostgreSQL** — schema in [prisma/schema.prisma](prisma/schema.prisma), migrations in [prisma/migrations/](prisma/migrations/)
- **Shopify App Bridge + Polaris** for the embedded UI
- **AI providers**: Anthropic, Gemini, OpenAI, HuggingFace, DeepSeek, Grok (see [app/services/](app/services/))
- **Vitest** for tests
- **Runtime**: Node, deployed on Railway from the [Dockerfile](Dockerfile); deploy mechanics as config-as-code in [railway.json](railway.json) / [railway.dbalert.json](railway.dbalert.json) / [railway.dbbackup.json](railway.dbbackup.json) (see [RAILWAY-SETUP.md](RAILWAY-SETUP.md) §0)

Own `/app/bulk` main-nav tab; legacy `/app/seo/bulk-meta` 302-redirects. ## Architecture invariants

- **Unified action handler.** Products, collections, pages, blogs, articles all route their actions through `handleUnifiedContentActions` in [unified-content.actions.ts](app/actions/unified-content.actions.ts). Do not add parallel handlers.
- **Translations write to Shopify AND the local DB.** Foreign values go to Shopify via `translationsRegister` (or the unstable CookieBanner endpoint) AND to Prisma (`ContentTranslation`, `ThemeTranslation`, etc.). A save is only successful if Shopify **echoes back** the keys — `userErrors` alone is not enough. Historic bug pattern: silent no-op when Shopify accepted the call but stored nothing. Conversely, always write the DB row **even when Shopify returns no digest** — `translationsRegister` requires a digest but Prisma does not (fields like `product_type` may lack one in some contexts).
- **Delete on Shopify must check the echo too.** `translationsRemove` can silently no-op. If Shopify does not confirm removal, do NOT delete the local DB row — otherwise state diverges.
- **Reload only refreshes known IDs.** Per-resource reload (e.g. `syncSingleProduct`) does not discover newly created Shopify resources. New resources appear only via full `syncAll*` runs.
- **UiDataLoader owns editor state.** [useUiDataLoader.ts](app/hooks/useUiDataLoader.ts) owns five cache refs (`deletedTranslationKeysRef`, `localTranslationsRef`, `savedPrimaryValuesRef`, `originalLoadedValuesRef`, `originalTemplateValuesRef`) plus a `resolve()` priority chain (foreign: deleted → localOverride → itemTranslation → fallback → empty; primary: savedPrimaryCache → itemField → fallback). **Items are read-only** — never mutate `item.translations` or item properties; go through the overlay refs. `resolve()` reads them.
- **Change detection uses the session load baseline**, not the live item. `getChangedFields` compares against the baseline captured at load — comparing against `item.body` etc. drifts and silently clobbers unrelated fields (e.g. a meta-description edit erasing `body_html` translations).
- **Primary saves invalidate foreign translations.** When primary content changes on templates, the server deletes stale foreign translations on Shopify. The client must invalidate `loadedTranslations`, `loadedTranslationsRef`, `localTranslationsRef`, and `deletedTranslationKeysRef` — otherwise stale foreign values reappear when switching locales. The single editor and the bulk editor (`invalidateStaleForeignTranslations`) both do this server-side too — echo-verified, global `marketId ""` rows only (market overrides survive).
- **Bulk edits go through `applyBulkDiff`** ([apply.server.ts](app/services/bulk-editor/apply.server.ts)) — the ONE write path. Three entrances: the sync route action (≤`MAX_SYNC_SAVE` cells), the `seoBulkMeta` write task, and the `bulkEditorTranslate` AI task. All validate the client diff server-side against the server-built column universe (`buildServerColumnsByType` — never trust client column claims) and gate plan/locale/market at **all three** (the `/api/ai` handlers are directly POST-reachable). Foreign translations write ONLY through the echo-verified `registerAndVerify` / `removeAndVerify` / `removeAndVerifyAcrossLocales` in `bulk-editor/translations.server.ts`. Failures are per **cell** (`BulkFailure.columnId`), never all-or-nothing per row. The task type stays `seoBulkMeta` even though the editor left the SEO section — renaming would break running tasks + `LONG_RUNNING_TASK_TYPES`.
- **Image rows are the alt-text surface.** The bulk editor's `image` row type is ONE row per product medium, with the Shopify **MediaImage GID as the row id** — so the alt translation rides on the row's own `translatableResource` (key `alt`, the only one a MediaImage has; verified live via Settings → Probes → Translation) and needs no sub-resource indirection. Only the DB mirror differs: `ProductImageAltTranslation` (keyed by the ProductImage CACHE row), the same store the single editor and the SEO bulk fix write. The primary write is `productUpdateMedia` via the shared `writeMediaAltText` — the product row's `img.alt` column (main image only) uses the identical helper, so there is one mutation and one echo rule. Cached images WITHOUT a `mediaId` are excluded from the row type (no valid row id, no write path — a product resync fills it in). Collection/article featured images ARE translatable, on their own `CollectionImage`/`ArticleImage` GID with the key `alt` (re-verified live 2026-08; an earlier probe run read "zero keys" only because the sampled image had no alt text set in the primary locale — see the empty-value trap below). They are NOT in the image row type: their alt lives on the CollectionImage record, NOT on the MediaImage of the same file — the probe found the collection's file in the Files library exactly once with an EMPTY MediaImage alt while the CollectionImage alt was set, so writing the file's alt would not change the collection's. The two GIDs are also not convertible into each other (same numeric id resolves to nothing). The row type UNIONS two sources: product media (`ProductImage`, mirror `ProductImageAltTranslation`) first, then every other image of the shop from the `MediaLibraryImage` cache (mirror `ContentTranslation` with `resourceType: "MediaImage"`) — the write path picks the store by whether a `ProductImage` row exists for the GID, never by the segment. The library segment therefore DROPS rows the product segment already serves (a `usageKind` that went stale between media syncs): listing one image twice is not cosmetic — the copies would READ from different stores while both WRITE to the same one, and a translation would save and come back empty. Because that drop happens after paging, every sweep over this loader (CSV export, candidate scan) must stop on the OFFSET, never on a short page. Which write path a row takes follows the same rule as its translation store: a `ProductImage` row ⇒ `productUpdateMedia` + `ProductImageAltTranslation`; otherwise `fileUpdate` + `ContentTranslation`.
- **The featured-image alt is the THIRD translation shape.** A collection's / article's `img.featuredAlt` column writes its PRIMARY value inline through `collectionUpdate`/`articleUpdate` (`image: { altText }`, the same call the single editor makes) and mirrors to `Collection.imageAltText`/`Article.imageAltText`. Its TRANSLATION is the only one whose Shopify target and DB row have different ids: Shopify stores key `alt` on the image's own `CollectionImage`/`ArticleImage` GID, while `ContentTranslation` sits on the PARENT with `key: "image_alt_text"` — exactly what `saveImageAltTextTranslation` in the single editor writes, so both editors read each other's rows. The image GID is cached nowhere and cannot be derived from the parent; `fetchFeaturedImageId` resolves it per row. `isFeaturedImageAltColumn` is the ONE predicate every branch asks (`translationKeyForColumn` returns the DB key, `persistTranslationRow` diverts before the sub-resource check, `fieldsOfGroup` maps it to `imageAltText`, and §6.6 invalidation has its own pass because neither half of the generic one can reach it).
- **Sub-resource translations ride on their OWN Shopify resource.** Metafield cells translate on the **Metafield GID** (key `value`), option names on the **ProductOption GID** and option values on each **ProductOptionValue GID** (key `name`) — never on the product's `translatableResource`. `translations.server.ts` owns the mapping (`isSubResourceColumn` / `subResourceTargetsForColumn` / `subResourceCacheFromRow`), `apply.server.ts` writes it through `persistSubResourceTranslations` with the same echo/digest rules as the row path, and `ContentTranslation.resourceType` is `Metafield` / `ProductOption` / `ProductOptionValue` — the exact strings the single editor writes, so both editors read each other's rows. A primary change to a metafield or option invalidates ITS OWN translations (same §6.6 rule, own resource id). An option-VALUES cell is ONE cell over N resources: it is written as a whole list, so the AI path merges over the entries that already have a translation instead of replacing them. Alt-texts are deliberately excluded (they ride on MediaImage and even the primary write needs the deprecated `productUpdateMedia`).
- **`translatableContent` only lists keys that HAVE a primary value.** A resource with an empty field returns no entry for it, which is indistinguishable from "this resource type cannot translate that field" — the trap that produced the wrong "collection/article images are not translatable" invariant above. Never conclude "not translatable" from an empty key list: probe a resource whose field is actually filled (`pickWithImage` in [api.translation-probe.tsx](app/routes/api.translation-probe.tsx) picks an alt-bearing sample for exactly this reason), or the answer is inconclusive, not negative.
- **A merchandising attribute is only readable once `attributesSyncedAt` is set.** `Product`/`Collection`/`Article`/`Page` carry a block of attributes the sync only learned to fetch in PLAN_CONTENT_CREATION Phase 0 (`vendor`, `tags`, `category*`, `templateSuffix`, `publishedAt`, `sortOrder`, `isSmart`/`sourcesJson`, `author`, `isPublished`, plus the `ProductCollection` membership rows). On a row written by an older sync those columns hold the migration DEFAULTS — `null`, `{}`, `true` — which is indistinguishable from "the merchant left it empty", the same trap as `SeoCrawlPage.metaRobots`. `attributesSyncedAt` is the discriminator and `attributesKnown()` in [attribute-sync.shared.ts](app/services/attribute-sync.shared.ts) is the gate every reader passes through: unset ⇒ show "unknown" and offer a reload, never a red "missing". The WRITE side enforces the mirror image: the mappers there return `{}` for a response that did not carry the block, so a partial query can neither overwrite what a full sync established nor stamp knowledge that never arrived — and `productCollectionRows` returns `null` (skip the rebuild) rather than an empty list (wipe the memberships). That module is also the ONE place where the attribute GraphQL selections live, and **there are FOUR product write paths, not one** — `syncAllProducts` and `syncProduct` in [product-sync.service.ts](app/services/product-sync.service.ts) (the latter is also what the `products/*` webhooks call, so that one is covered) plus the two route-local ones in [api.sync-products.tsx](app/routes/api.sync-products.tsx) and [api.sync-missing-products.tsx](app/routes/api.sync-missing-products.tsx). Each carries its OWN inline product query, so a new product column has to be added to every one of them; interpolating the shared constants is what keeps that mechanical instead of a memory exercise. A path that fetches a NARROWER selection is handled, not trusted: the mappers require EVERY key of the block to be present and return `{}` otherwise, because a half-delivered block written as defaults is worse than no write at all. `Collection.sourcesJson` stores a `{shape, apiVersion, data}` envelope, never a bare tree: the 2025-10 `ruleSet` and the 2026-07 `sources[]` models are not interchangeable and a reader must not have to guess which one a row holds.
- **`Collection.ruleSet` is a LOSSY back-projection of the 2026-07 `sources` model, not a second view of it.** Measured on a live shop (2026-08, Settings → Probes → Collection Model): a source written as `productTag { relation: TAGGED_WITH, values: […], matchType: ANY }` reads back through `ruleSet` as `{column: "TAG", relation: "EQUALS", condition: "…"}` — the relation is coerced and the condition's OWN `matchType` (the new model has two levels of it, one per source and one per condition) is dropped entirely. Structures with no legacy equivalent at all — exclusions, multiple named sources, variant targeting — cannot project and are simply absent; that is the same mechanism behind the documented "collections using new features are filtered from pre-2026-07 query results". So from 2026-07 on, READ `sources`, never `ruleSet`: an editor that reads `ruleSet` and writes it back would silently change a collection's membership, which is the §2.4 read-only rule one level deeper. Editing a source is also a DIFF, not a replace (`conditionsToCreate`/`ToDelete`/`ToUpdate` + `selectionsToAdd`/`ToRemove`, each keyed by an id from the read path), which is what makes "don't touch what you cannot render" mechanical rather than a discipline.
- **Pages, articles and blogs have NO Shopify webhook — the editor's save is the only moment anything knows.** Products and collections are covered by `products/update` / `collections/update`, so [webhooks.products.tsx](app/routes/webhooks.products.tsx) enqueues IndexNow from them; for the other three a published page reached IndexNow only via a manual catalogue send. `shouldEnqueuePublishChange` ([index-now.service.ts](app/services/seo/index-now.service.ts)) mirrors `shouldEnqueueProductChange` deliberately — live now ⇒ submit; just became a 404 ⇒ submit, because reporting removals is half of what IndexNow is for; never live ⇒ nothing, since a draft's URL is an address no engine holds. That last rule is why the enqueue sits at the TRANSITION and not at create: everything this app creates is created unpublished, so a create-time ping could only ever announce drafts. `previousPublished` comes from the cache and is reported as UNKNOWN when `attributesSyncedAt` is unset — the column defaults to `true`, so reading it as "was visible" would make the first save of every draft look like a publish. [index-now-content.server.ts](app/services/seo/index-now-content.server.ts) owns it, keeps the URL building pure and testable, and never throws: the save has already happened.
- **On a primary-locale save, a field's PRESENCE is not the merchant's INTENT.** `buildFieldsForSave` ([useEditorAutoSave.ts](app/hooks/useEditorAutoSave.ts)) filters to changed fields only for FOREIGN locales; a primary save carries every field the config declares. For text that is harmless — writing the same title back changes nothing. For the §Phase 3 merchandising attributes it is data loss, because Shopify REPLACES rather than merges and the values arrive from a cache that may never have been attribute-synced: a title edit would delete every tag, clear the vendor, reset the theme template and PUBLISH a hidden article. `changedFields` is the discriminator and `attributeInputFor` ([content-attributes.shared.ts](app/services/content-attributes.shared.ts)) is the gate — no `changedFields` ⇒ write no attributes, because a caller that does not say what changed is indistinguishable from one where nothing did. `productType` in [update.actions.ts](app/actions/product/update.actions.ts) has carried this exact guard since long before those fields existed; it is the precedent, not an exception. The same module is also the ONE place that validates them: `status` and `sortOrder` are GraphQL ENUMS, and a bad enum fails at the SCHEMA level — a top-level `errors` array with `data: null` that never reaches `userErrors`, so a forwarded bad value makes the whole save read as a success while nothing was written. Unrecognised values are dropped and reported. And an attribute a resource does not have is filtered out rather than sent: `sortOrder` on a page makes Shopify reject the WHOLE input, taking the merchant's text edits with it. UI side: these fields carry `translationKey: ""`, which `resolve()` short-circuits to the primary value — sent down the foreign chain they would resolve to `""` and a Polaris `Select` would render its first option, showing an ACTIVE product as DRAFT and a hidden page as visible.
- **A handle change owes the old URL a redirect, and the redirect is a DIFF over the shop's existing ones.** Changing a handle silently 404s every link to the old address, so both primary write paths — the single editor's `updateContent` and the bulk editor's `field.handle` column — run the same decision through [handle-redirect.shared.ts](app/services/seo/handle-redirect.shared.ts) (pure) and [handle-redirect.server.ts](app/services/seo/handle-redirect.server.ts) (Shopify). Four rules are load-bearing. (1) The target is the handle Shopify **echoed back**, not the one submitted: every write path sanitizes the slug and every update mutation already selects `handle`, so trusting the sent value is an assumption whose failure mode is a redirect onto a 404 plus a message saying the old URL is covered. (2) It is a diff, never a blind create: renaming a→b→c must REPOINT `/a→/b` to `/a→/c` (otherwise this app's own `redirect-chains.ts` reports the chain it just made), and renaming back a→b→a must **delete** `/a→/b` — that path is a live page again and Shopify serves the redirect in preference to it, so leaving the row makes the renamed object unreachable at its own address. Lookups go through `listRedirects(query)` and are re-filtered by exact path, because the query is a search and a near-miss must never be repointed. (3) It can never fail the save: the content update has already happened, so every failure is a NOTE and both call sites catch. (4) Foreign-locale handles are out of scope as a SCOPE decision, not as an unknown: **measured 2026-08 on a live translating shop** ([api.redirect-locale-probe.tsx](app/routes/api.redirect-locale-probe.tsx), Settings → Probes → Translation), a throwaway `/<probe>` → `/<target>` with both sides distinctive answers BOTH halves of the question — `/en/<probe>` returns 301, so a locale-prefixed path DOES match the path-based redirect table, and its `Location` is `/en/<target>`, so the prefix is CARRIED onto the target. One UNPREFIXED row therefore serves every locale and a per-locale row would be redundant, the opposite of the pessimistic reading the gap was built on. Extending the foreign-handle write paths is consequently possible and is a behaviour change to be asked for, never assumed. Keep the probe route: this is re-measurable in one click rather than re-argued. Blogs redirect their own `/blogs/<handle>`, but their ARTICLES' URLs move with them and Shopify redirects have no wildcards, which is why that case reports `blogArticlesUncovered` rather than a plain "created". Notes travel as CODES ([handle-redirect-message.ts](app/utils/handle-redirect-message.ts) owns the wording) — the app ships in three languages, and the save response is read in two places.
- **Storefront URLs handed to an external system use the PRIMARY domain.** Shopify 301s every storefront URL on `*.myshopify.com` to the shop's primary domain, so a myshopify URL published outwards is a non-canonical redirect — and for a host-verified protocol it is worse: the verification fetch ends on a different host than the one declared, which is what IndexNow's ownership check is about (it cost this app a feature that could not work on any shop with a custom domain). `fetchPrimaryDomain` in [shop-domain.server.ts](app/utils/shop-domain.server.ts) is THE resolver (sitemap + IndexNow use it; the crawler and AEO carry their own equivalent). IndexNow additionally PERSISTS the resolved host on `SeoIndexNowConfig.host` so webhooks can build URLs without a lookup, and re-syncs it on every section visit — a merchant who connects a custom domain later is corrected without minting a new key.
- **An IndexNow key file must sit at the storefront ROOT — measured, not assumed.** Serving it from the app proxy (`/apps/contentpilot/indexnow-key`) works as delivery (probe on a live shop: 200, no redirect, content matches) but every submission still comes back `422 InvalidRequestParameters — "not related to your site verified through the keylocation parameter"`, because a non-root `keyLocation` verifies only its own sub-path. It is a SCOPE rule, not a host rule: do not re-diagnose it as a domain problem. So `keyLocation` names `https://<host>/<key>.txt` and a Shopify **URL redirect** maps that root path onto the app proxy — one host end to end, no `cdn.shopify.com` hop (a cross-host hop is what an ownership check objects to). Confirmed working on a live shop: `/<key>.txt` → 301 (same host) → app proxy → 200, submission **202 Accepted** — the engine does follow a same-host 301, and a root keyLocation covers the whole site. Lifecycle + echo rule in [index-now-key-file.server.ts](app/services/seo/index-now-key-file.server.ts); the redirect GID lives on `SeoIndexNowConfig.keyRedirectId`, and both the section loader and the sweep recreate it when it is missing. [api.indexnow-probe.tsx](app/routes/api.indexnow-probe.tsx) (Settings → Probes → Translation) fetches the key file hop by hop and fires one real submission, so this stays re-measurable in one click rather than re-argued.
- **One crawl, two STEPS of one tab.** `runCrawl` ([crawl.service.ts](app/services/seo/crawl.service.ts)) stays the ONLY live-fetch surface. `/app/seo/crawl` shows both halves behind `?view=delivery|onpage`, as two `StepTile`s (the AEO section's shape, and the same relationship: a page that is not delivered has no on-page quality to judge). They were two nav chips at first — which only made merchants ask which of the two crawls they were supposed to run. The loader builds ONLY the requested half (step 2 loads every snapshot row + head drift + the shop name), which is why switching steps is a navigation and not local state. `/app/seo/onpage` remains as a redirect carrying its `?tab=` across, for bookmarks and the dashboard's deep links. Step 2's loading lives in [onpage-report.server.ts](app/services/seo/onpage-report.server.ts), its rendering in [OnPageReportView.tsx](app/components/seo/crawl/OnPageReportView.tsx) (tiles and sections separately, because they land in different cards). The page order is fixed: **explanation → scan → step badges → results**. `CrawlSnapshotHeader` is the SCAN card — the run button, the run's own warnings, and controls that change what the crawl DOES (the external-link opt-in) — and nothing else; the result tiles sit in their own card BELOW the two `StepTile`s, since they belong to whichever step is open. With the tiles inside the scan card the page read "here is the scan, here are ITS numbers, and now, afterwards, here is which of two reports you were looking at". The crawl diff is a RESULT too, so it sits directly above the result tiles, not above the scan card. Both halves read the SAME snapshot through `loadLatestSnapshot` ([crawl-snapshot.server.ts](app/services/seo/crawl-snapshot.server.ts)); never add a second single-flight query or a second header. Report primitives live in [components/seo/crawl/](app/components/seo/crawl/), not route-local.
- **A translated resource is served under a TRANSLATED handle.** `/es/products/caja-kumiko-…` and `/products/kumikobox-…` are one product, and the content cache only stores the primary handle — so `resolvePathsToResources` ([url-resolver.server.ts](app/services/seo/url-resolver.server.ts)) falls back to `ContentTranslation` (`key: "handle"`) for the handles the primary lookup missed. Without it every foreign-locale URL of a translating shop resolves to `id: null`, which on the crawl report means no "open in editor" on most of the catalogue. Shopify ALSO answers 200 for the primary handle behind a locale prefix (`/es/products/<german-handle>`), serving the untranslated `<title>` and canonicalising to the translated URL — which is why duplicate detection runs only over `selfCanonicalPages`: a page whose canonical points elsewhere is not indexed under its own URL and cannot be half of a duplicate-content finding. Skipping that reported one product as five duplicates on every multilingual shop.

- **Every path rule must survive a locale prefix.** Shopify serves each storefront path under every published locale, so a rule anchored at `/cart` or `/policies` silently applies to the primary locale only. `stripLocalePrefix` / `localeVariants` ([locale-path.shared.ts](app/services/seo/locale-path.shared.ts)) is THE stripping rule — the crawl denylist, `expectedNoindexReason` and `hasEditableMetadata` all test against the raw path AND the stripped one (an additional match, never a replacement, so `/de/cart-bags` stays allowed). The denylist matching only the raw path is how `/it/cart`, `/es/account` and `/fr/checkout` got crawled — including the PII-adjacent ones the denylist exists for — and then reported as on-page findings.
- **Some pages have no metadata surface AT ALL, and reporting them is not a finding.** `shopPolicyUpdate` takes `{ type, body }` — there is no `seo` input and no metafield, so every `/policies/*` page of every shop is served without a meta description, by construction. `/collections/all` is Shopify's reserved virtual listing, not a Collection record (`all` cannot be taken as a handle), and a paginated `?page=N` URL carries page 1's metadata. `hasEditableMetadata` ([onpage.service.ts](app/services/seo/onpage.service.ts)) is the one predicate; the missing-description list, both duplicate groupings and the CSV export share it, and the excluded count is SHOWN (`metadataSkipped`), never silently dropped. Without it a five-locale shop's whole meta-description category was pages nobody can fix, and `?page=2` vs `?page=3` of one listing reported each other as duplicate content. `?page=1` is a separate matter: it is the same document as the bare URL, so `normalizeCrawlUrl` drops it rather than crawling the page twice.
- **A policy page is a deep-link target but not an `AuditType`.** `/policies/refund-policy` resolves to a real `ShopPolicy` (its handle IS the type in kebab case — the record has no handle column), so the crawl report can offer "open in editor" into `/app/policies?select=<gid>`. It is NOT part of the audit: no SEO title, no meta description, no coverage score. `DeepLinkType` / `isAuditType` ([resource-types.shared.ts](app/services/seo/resource-types.shared.ts)) are the split — every `Record<AuditType, …>` map (dashboard buckets, "Fix with AI", head drift) narrows with `isAuditType`, and the report UI uses the wider type. The vocabulary lives in its own module because `crawl.service.ts` needs `isAuditType` as a value and `audit.service.ts` already imports crawl.service.
- **`noindex` overlaps the sitemap section, and the overlap is the point.** The sitemap tab decides which pages SHOULD be excluded; the on-page step reports which ones ARE excluded without anyone asking. `loadExpectedNoindexReasons` (crawl-snapshot.server.ts) is the one place that knows what counts as deliberate: APPLIED (never merely suggested) `SeoSitemapExclusion` rows, and UNLISTED products — Shopify serves those with `noindex,nofollow` itself (documented and measured, see [sitemap.service.ts](app/services/seo/sitemap.service.ts)), so without that entry every unlisted product tops the report and the dashboard as a critical, unexplained exclusion.
- **A robots directive can carry a VALUE.** `max-image-preview:none`, `max-snippet:`, `max-video-preview:` and `unavailable_after:` are valid and common; taking "everything after the colon" as the token (which is right for a `googlebot:` user-agent prefix) reduces the first to the bare word `none` — shorthand for `noindex,nofollow`. That put perfectly indexable pages at the top of the dashboard. `robotsTokens`/`deriveIndexability` live in [indexability.shared.ts](app/services/seo/indexability.shared.ts) and ONLY there: `crawl-diff.ts` needs the same rule in component scope and its hand-copied duplicate is how that bug shipped twice.

- **An empty crawl column is never evidence.** `SeoCrawlPage.metaRobots == ""` means "nothing served" OR "row written before the column existed" — indistinguishable, exactly like the `translatableContent`/`jsonLdTypes` traps. `indexabilityKnown` is the discriminator and is set ONLY when a body was actually parsed. Consequences that are load-bearing: pre-existing columns (`title`, `metaDesc`, `canonical`, `h1Count`, `wordCount`) hold real values on old snapshots and are judged on 2xx alone (`judgeable` in [onpage.service.ts](app/services/seo/onpage.service.ts) falls back when NO row knows); rules built on the NEW columns (`h1First`, `imgMissingAlt`) must render "unknown", never "none found"; and `diffCrawls` hides the indexability half unless BOTH snapshots know, or the first crawl after a deploy reports the whole catalogue as changed. Never read an empty column as "fine".
- **Every on-page category is filtered against its own false positives.** A `noindex` is often deliberate (`EXPECTED_NOINDEX_PATTERNS` + APPLIED — never merely suggested — `SeoSitemapExclusion` rows). Shopify canonicalises `/collections/x/products/y` → `/products/y` correctly, so only demonstrable canonical defects are reported and a canonical whose target was never crawled yields nothing. Thin content is a percentile WITHIN a `resourceType` (`countWords` keeps header/aside/theme boilerplate, so an absolute threshold is meaningless), with types under 20 pages skipped AND said so. `alt=""` counts as missing, which is why that category says "without alt text", never "error". These filters are the feature — dropping one turns the tab into noise.
- **The canonical host comes from the crawled URLs, never from a lookup.** `fetchPrimaryDomain` falls back to the myshopify host when the Admin call is throttled, while every crawled URL is normalized to the PRIMARY domain — one bad lookup would flag every page as a critical "canonical points at a foreign domain". `canonicalHostFromPages` ([onpage.service.ts](app/services/seo/onpage.service.ts)) is the resolver; the looked-up domain goes in as an alias only.
- **External-link checking is a SECOND pass with its own regime, after the crawl is persisted.** [external-links.ts](app/services/seo/external-links.ts): 6 parallel but max 2 per host (Shopify's shield does not apply to strangers; manners toward one host still do), HEAD then a one-byte GET on 403/405/501 (a huge share of hosts refuse HEAD while serving fine — without the fallback the report calls healthy links dead), dedup by the FULL url including query, and `isPrivateOrLoopbackHost` re-checked on EVERY redirect hop. 403/429 is a bot shield, NOT a dead link — the same rule as `isBotBlockStatus` internally. A hard 120s budget with the task heartbeat wired through it, and everything it did not reach is persisted as `EXTERNAL_NOT_CHECKED` rather than dropped: a missing row is indistinguishable from a healthy one. The pass must never be able to downgrade a persisted crawl to "failed". Opt-out on `AISettings.seoCrawlExternalLinks` (default on); with it off the UI shows "—", never 0.
- **Redirect chains need no crawl.** `A → B → C` is fully derivable from Shopify's own redirect list ([redirect-chains.ts](app/services/seo/redirect-chains.ts), pure + client-safe). Paths match case-insensitively and slash-normalized (Shopify does too); an absolute target on the primary host is followed, a foreign host ends the chain, and with no known primary host every absolute target ends it — a missed finding, never a wrong fix. A loop gets no auto-fix (there is no end target to choose) and each cycle is reported once, not once per member. Resolving repoints only the FIRST redirect and re-derives the chain server-side; intermediates stay (they can carry their own inbound links) and the UI must say so.
- **Crawl/on-page CSV exports are resource routes and gate themselves.** Directly GET-reachable, so `meetsPlan(plan, "pro")` lives in the route — same class as the `/api/ai` handlers. No row cap (UI_ROW_CAP is a rendering limit; getting past it is why merchants export). One serializer, [csv-export.ts](app/services/seo/csv-export.ts): `;` + BOM for the new exports (Excel DE), and a formula-injection guard because these files carry `<title>` text and URLs this app did not author.
- **Stock is money, so the echo rule is stricter and the arithmetic is forbidden.** Phase 4 MIRRORS inventory into `InventoryLevel` / `Location` / `ProductPublication`, but nothing reads those rows to render the panel: quantities move from orders, returns and other apps between two page loads, so the panel reads Shopify LIVE and a failed load says so rather than showing a stale number. `inventorySetQuantities` takes an ABSOLUTE quantity and [commerce-write.server.ts](app/services/commerce-write.server.ts) always pairs it with `compareQuantity` (`ignoreCompareQuantity: false`), so a value that moved under the merchant's feet is REFUSED (`stockChangedMeanwhile`) rather than overwritten; computing `cached + delta` is the classic source of inventory drift and this module deliberately offers nothing to compute it with. A write counts as successful only when Shopify echoes the new quantity back AND it matches, per change — `userErrors: []` is not enough, and a partial apply mirrors only its confirmed half. Only `on_hand` is writable: `available` is DERIVED (on hand minus open commitments) and writing it would contradict them. **Untracked is not zero** — `tracked: false` means Shopify keeps no count, `null` means never synced, and rendering either as 0 tells a merchant they are sold out of something they can sell without limit. `commerceSyncedAt` is that block's discriminator, exactly like `attributesSyncedAt`; `variantCommerceColumns` returns `{}` for a response that did not carry the block so a narrower query can neither overwrite nor stamp knowledge. Stock lives on its OWN route ([api.product-commerce.tsx](app/routes/api.product-commerce.tsx), plan-gated in the route) and saves through its own button, never through the content save — a volatile number in the editor's flat value map would be stale by the time anyone pressed save.
- **`status: ACTIVE` is not visibility, and `ProductPublication` is what finally says so.** A product published to no sales channel is invisible everywhere and the Shopify admin does not mention it on the product page either. An empty publication list is therefore a MEANINGFUL state, which is why `productPublicationRows` returns `null` for a response that did not carry the block rather than an empty list: wiping on a partial response would manufacture exactly the alarming state the feature exists to reveal. Shopify's own `isPublished` is taken verbatim (it already accounts for a future publish date) — recomputing it from the date is a second answer to one question, and the two drift.
- **A rule-based collection is untouchable in BOTH directions, and "unknown" counts as rule-based.** Leaving a smart collection is undone by its rule within seconds; JOINING one is refused by Shopify, and because `productUpdate` is atomic that refusal takes the merchant's title, description and SEO edits with it. `Collection.isSmart` is `NOT NULL DEFAULT false` on a column added to an existing table, so `attributesSyncedAt` gates every read of it — an unsynced row is UNKNOWN, and `diffCollectionMembership` refuses unknown as well as known-automated, because not adding a membership costs a click while adding one wrongly costs a text edit. Membership is a JOIN/LEAVE diff whose BEFORE side is the cache; the picker UNIONS the shop's collections with the product's own memberships, since a membership it cannot show is one it would silently remove.
- **Backticks inside a `#graphql` comment terminate the template literal.** Every GraphQL string in this repo is a backtick template, and a comment like ``# mirrors `sourcesJson` `` ends the string mid-query — a `TS1005: ',' expected` whose reported column points at innocent code. This has cost four separate debugging rounds ([apply.server.ts](app/services/bulk-editor/apply.server.ts), [collection-rules.server.ts](app/services/collection-rules.server.ts), [update.actions.ts](app/actions/product/update.actions.ts) twice). Use quotes or bare words inside GraphQL comments.
- **One field→translation-key map.** `FIELD_TO_TRANSLATION_KEY` / `fieldTranslationKeyMap(resourceType)` in [shopify-content.service.ts](src/services/shopify-content.service.ts) is THE map (ShopPolicy translates `body`→`body`; every other type maps `body`/`description`→`body_html`, `seoTitle`→`meta_title`, `metaDescription`→`meta_description`, `productType`→`product_type`, `summary`→`summary_html`). Never re-declare it — historic copies drifted. `TranslatableResourceType` enum is `PAGE`/`ARTICLE`/`BLOG`/`COLLECTION` (the `ONLINE_STORE_*` names were removed with 2024-10).

## Deploy-critical gotchas

- **Only ONE theme app extension per Shopify app.** All storefront/theme blocks (JSON-LD, social-meta, app embeds) MUST live under [extensions/storefront/](extensions/storefront/). Creating a second `type = "theme"` extension silently breaks `shopify app deploy`.
- **The extension has a hard 100 KiB (102400 bytes) Liquid budget.** Every `extensions/storefront/blocks/*.liquid` counts together; `assets/` does not (served statically — that's why the block logic lives there). Over budget, the CLI fails with `bundle: Extension Liquid content size exceeds 100 KB limit`. The commented sources are already over it, so deploy via `npm run deploy` ([scripts/deploy-minified.mjs](scripts/deploy-minified.mjs)) — it minifies the blocks in place, deploys, and restores the sources in a `finally` (also on failure/Ctrl-C). **Never commit minified blocks**; `blocks/` stays commented in git. Minification skips `<script>`/`<style>`/`<pre>`/`<textarea>`/`{% raw %}` and every `{% … %}` / `{{ … }}` interior byte-identically, so comments inside a JSON island buy no headroom — when it gets tight, move markup into `assets/`. Check with `npm run minify:blocks`.
- **Never add a `postdeploy` script to package.json.** npm auto-runs `pre<x>`/`post<x>` around every script, so a `postdeploy` entry fires after each `npm run deploy` — *after* the extension version is already released. It used to run [scripts/migrate-baseline.js](scripts/migrate-baseline.js) (a DB migration, unrelated to the Shopify deploy) and turned successful releases into a red exit code, inviting a retry that publishes a second version. Railway never called it: it starts via `npm run start:production` → `run-all-migrations.js`. That start command comes from [railway.json](railway.json) — every Railway service here builds with the `Dockerfile`, whose `CMD` (`npm run start` — no migrations) the config file overrides. A `Procfile` and a `nixpacks.toml` used to sit alongside it describing a build path Railway never takes; both were deleted rather than left as a second, contradicting answer. Deploy mechanics live in `railway.json` / `railway.dbalert.json` — see [RAILWAY-SETUP.md](RAILWAY-SETUP.md) §0 for which file belongs to which service and what can only live in the dashboard. Run the baseline migration explicitly with `npm run prisma:migrate`.
- **The DB backup is a fourth Railway service, and its dump is verified before it counts.** [db-backup.mjs](scripts/db-backup.mjs) (config in [railway.dbbackup.json](railway.dbbackup.json), env table in [RAILWAY-SETUP.md](RAILWAY-SETUP.md) §0) dumps to Cloudflare R2 nightly. Three rules are load-bearing: `pg_dump` must be **>= the server major** or it refuses the dump — an unknown version on either side counts as incompatible, never as fine, and the Dockerfile's unversioned `postgresql-client` is what gets pinned when Railway's Postgres moves; the dump is fed back through `pg_restore --list` before upload, because a truncated archive is otherwise indistinguishable from a small database until the restore you attempt under pressure; and retention never deletes the newest `BACKUP_KEEP_MINIMUM` dumps regardless of age, so a cron that silently stopped cannot have "everything is old" read as "delete everything". `DATABASE_URL` is expanded into `PG*` env vars rather than passed as argv — a connection string on the command line is readable from `/proc` by anything else in the container.
- **App embeds cannot inject `<head>` CSS.** `{% stylesheet %}` is not available in app blocks; styles must live inline or in a section/block that participates in the theme's asset pipeline.
- **Meta title/description on pages, blogs, articles ≠ native `seo` field.** They live in `global.title_tag` / `description_tag` **metafields**. Clearing requires `metafieldsDelete` — setting an empty string does NOT clear.
- **`metafieldsSet` with `""` is rejected** ("Value can't be blank") — clear a metafield via `metafieldsDelete` (`MetafieldIdentifierInput`: `ownerId`+`namespace`+`key`; the old GID-based `metafieldDelete` was removed 2025-01). Always send `type` on `metafieldsSet` (required when creating without a definition); max 25 per call, atomic upsert.
- **Phase 4 added `write_inventory,read_locations,write_publications` to BOTH TOMLs — the second scope change this app has made.** Each one forces a one-time re-consent of every installed merchant, which is why the rule is that all new scopes ship in ONE deploy: two re-consent rounds in a row is what loses merchants. `read_inventory`/`read_publications` are deliberately NOT requested — a `write_*` scope normally grants the read, and every superfluous scope is a point in the App Store review. An in-app banner explaining the re-consent was built and then removed as unwanted — do not reintroduce one without asking. `AISettings.commerceNoticeDismissedAt` is its leftover column, unused and kept only because dropping a possibly-applied migration is the riskier error.
- **Alt-text writes: `productUpdateMedia` for PRODUCT media, `fileUpdate` for every other image.** The app now declares `read_files,write_files` (added for the bulk editor's image rows — the scope change forced a one-time re-consent of every installed merchant; do not add scopes casually). `productUpdateMedia` is product-scoped and cannot address images outside the catalogue, which is what `fileUpdate` is for; product media deliberately keep the deprecated-but-tested `productUpdateMedia`, the same call the single editor makes. Both go through the echo rule (`writeMediaAltText` / `writeFileAltText` in apply.server.ts). Mirror to DB with `altTextModifiedAt: new Date()` so the self-triggered `products/update` webhook (5-min preserve window) doesn't overwrite the fresh value.
- **Variant pricing is synced in the regular product sync** (`price`/`compareAtPrice`/`barcode` on `ProductVariant`; before this, variant rows only appeared after opening the image manager). The variant upsert must NOT `deleteMany`+recreate — `galleryJson`/`imageKey` come from the image manager; upsert on `id` and delete only ids Shopify no longer returns. Products with >100 variants are flagged `hasMoreVariants` (remainder uncached, editable in the Shopify admin).
- **Partial SEO saves clobber the untouched half.** Sending `seo: { title }` alone on products/collections wipes the primary meta description. Always send both halves or preserve the untouched value.
- **Markets: gate on `status === 'ACTIVE'`, not deprecated `enabled`.** Secondary markets often have `webPresences: []` and share the primary web presence. Do not require web-presence locales to enumerate a market.
- **Theme keys need explicit filename routing on primary save.** In `templates-update.action.ts`, `resolveFilename` maps resource types to theme file names:
  - `ONLINE_STORE_THEME_LOCALE_CONTENT` + `ONLINE_STORE_THEME` → `locales/<primaryLocale>.default.json` (Shopify lowercases regional codes: `pt-BR` → `pt-br`; resolve robustly, do not hardcode)
  - `ONLINE_STORE_THEME_SETTINGS_DATA_SECTIONS` + `ONLINE_STORE_THEME_SETTINGS_CATEGORY` → `config/settings_data.json` (values live under `current.*`)
  - Unmapped resource types silently drop from the Shopify push while still writing the DB — that's a false-success bug pattern.
- **Autofix-normalized richtext: mirror the PUSHED value to DB, not the raw one.** If autofix rewrites a richtext value (`test<p></p>` → `<p>test</p>`) before writing `config/settings_data.json`, STEP 2b of the update handler must mirror the normalized value into `ContentTranslation`. Mirroring the raw value diverges DB from file → next save can't find the old value → save appears to no-op.

## Layout widths — every page and column spends a token, none invents a number

How wide a page or a column is is app-wide state, not a per-route decision: surfaces of the same kind that disagree by a few hundred pixels make the app look like it was assembled from parts, and "make the SEO pages 10% wider" turns into a hunt through routes. Every width lives ONCE, in the `:root` block of [responsive.css](app/styles/responsive.css) next to `--app-page-padding` — the same single-source pattern that variable already established. **No route, component or stylesheet hardcodes a page or column width.**

**Page width** — pick one of three classes for the route's outermost content wrapper:

- `.app-page-width` (`--app-page-width-content`) — reading-width pages: prose, forms, report tables. SEO sections ([app.seo.tsx](app/routes/app.seo.tsx)) and Tasks ([app.tasks.tsx](app/routes/app.tasks.tsx)) use it, deliberately at the same width.
- `.app-page-width-narrow` (`--app-page-width-narrow`) — focused single-task pages that are mostly one list of checkboxes or fields ([app.bulk_.translate.tsx](app/routes/app.bulk_.translate.tsx)).
- `.app-page-width-full` (`--app-page-width-full`, currently `none`) — data grids that turn every extra pixel into column width ([app.bulk.tsx](app/routes/app.bulk.tsx): `BulkGrid` gives uncapped columns `1fr`, so any margin is width thrown away), and sidebar+content layouts that are not reading-width content ([app.settings.tsx](app/routes/app.settings.tsx)). Stated explicitly rather than left off, so "uncapped" reads as a decision.

**Column width** — spent as `width: var(--…)` in the component's inline style (the way `--app-page-padding` is already used):

- `--app-list-column-width` — every "pick an item" column: the item list on the content pages and direct translations ([UnifiedItemList.tsx](app/components/unified/UnifiedItemList.tsx)), the Settings tab nav, the Menus list. They were 330/250/350px; the content list was the one that was right, so it set the token.
- `--app-editor-sidebar-width` + `-min-width` / `-max-width` — the content editor's right-hand SEO/bulk panel. The user drags it, so the token is only the DEFAULT it opens at plus the drag bounds; they live here anyway so the panel can be recycled elsewhere without re-deriving them.

Four mechanics that are easy to get wrong:

- **On a Polaris page the class goes on the `.app-page-content` frame**, alongside it — capping the FRAME keeps its `--app-page-padding` gutter and its inner scroll container (`.app-page-content > *`) intact, while an extra wrapper div would break the single-child scroll rule. `<Page fullWidth>` must stay: without it Polaris' own ~1000px cap wins before ours is reached.
- **The width classes carry no padding on purpose.** `.app-page-content` already owns its gutter, and a second `padding` declaration on the same element would win or lose by rule order. Non-Polaris routes keep their own `padding` in the inline style.
- **A resizable width starts as `null`, not as the number.** [UnifiedContentEditor.tsx](app/components/UnifiedContentEditor.tsx) renders `sidebarWidth ?? "var(--app-editor-sidebar-width)"` and, on the first drag, measures what that rendered as (`getBoundingClientRect`) instead of restating it. Seeding the state with `useState(320)` would put the default in a second place, which is exactly what drifts.
- **The drag bounds are read off the tokens per drag** (`getComputedStyle().getPropertyValue`), and a value that doesn't parse as px drops its half of the clamp rather than becoming `NaN` — `Math.max(NaN, …)` would make the panel unresizable.

## Single-language shops (one shop locale) — mandatory rules for every new UI

A shop with only its primary locale must never be offered translation UI it cannot use. These rules are not optional polish; apply them to **every new button, bar or section** that touches locales. Reference implementation: [LocaleAvailabilityContext.tsx](app/contexts/LocaleAvailabilityContext.tsx) + [DisabledActionTooltip.tsx](app/components/DisabledActionTooltip.tsx).

- **Locale buttons/bars: REMOVE, don't disable.** Anything that switches between languages (locale chip rows, `UnifiedLanguageBar`, `MobileToolbar`'s locale row, the keyword/glossary/dashboard locale bars) renders nothing at `locales.length <= 1` — a single permanently-active button is noise. Drop the surrounding `<Card>`/wrapper too so no empty box is left: `shouldRenderLanguageBar()` in [UnifiedLanguageBar.tsx](app/components/unified/UnifiedLanguageBar.tsx) is the caller-side twin of the bar's internal emptiness check. Kill the Ctrl+click hint with the bar (the primary locale can't be toggled off).
- **Everything else: DISABLE + tooltip, don't hide.** Translate, translate-to-all-locales, copy-to-all-locales, "Accept & Translate", alt-text translation, per-option/metafield 🌍 — all stay visible, greyed out, with `t.common.requiresSecondLanguage` as the tooltip. Hiding them makes merchants think the feature is missing.
- **Get the flag from the context, not from props.** Inside the editor tree call `useSingleLocaleHint()` — it returns `undefined` when the shop is multi-language (so `disabled={... || !!singleLocaleHint}` and `<DisabledActionTooltip hint={singleLocaleHint}>` are no-ops) and the reason string otherwise. `UnifiedContentEditor` provides `LocaleAvailabilityProvider`; components outside it (image manager panels that receive `shopLocales`/`enabledLanguages` as props) derive the same hint locally.
- **Disabled controls need the wrapper.** Browsers do not dispatch pointer events for a disabled control, so a bare Polaris `<Tooltip>` around it never opens. Always wrap with `DisabledActionTooltip`. In an `ActionList` (no hover tooltip possible) use `disabled` + `helpText` instead.
- **Whole sections that only exist for translation** (e.g. the hreflang audit): mark the descriptor `requiresMultipleLocales` ([seo-sections.ts](app/config/seo-sections.ts)), grey the nav chip with a **🌐** marker (never 🔒 — that reads as "upgrade your plan") and render the explanation in place of the section body. A plan gate outranks the language gate in both the marker and the body.
- **Never gate on a failed lookup.** `getCachedShopLocales` swallows non-401 errors and resolves with `[]`, so an empty list means "lookup failed", not "one locale" — treat it as multi-language. Do not `catch` around it: it re-throws 401 on purpose so the request can re-authenticate.
- **Handlers stay defensive anyway.** The client gate is UI only; every `targetLocales = enabled.filter(l => l !== primaryLocale)` path keeps its `length === 0` guard, and server actions keep returning a successful no-op.
- **Exception — Direct translations.** `/app/direct-translations` targets *all* published locales including the primary (the source string is arbitrary storefront text), so its translate buttons stay enabled with a single locale. Only its locale bar disappears.

## Auth / boundaries

- Shopify auth + session handled by the standard `@shopify/shopify-app-remix` flow.
- Multi-tenant: every DB row is scoped by `shopId`. Translations are additionally scoped by `locale`, and theme content by `themeId` + `marketId`.
- **`ThemeTranslation` unique key includes both `themeId` AND `marketId`.** Accessor: `shop_resourceId_groupId_key_locale_themeId_marketId`. It is the only translation table folding both.

## Working agreement

- **Every larger or system-relevant change ends with a review pass.** Once the rebuild is finished (and typecheck + tests are green), run an independent review agent over the diff — `/code-review high` on the branch, or a subagent with the same brief — and then FIX what it finds before reporting the work as done. "System-relevant" = anything touching a write path, translation/sync logic, auth or plan gating, a shared component or context used across pages, DB schema or migrations, deploy scripts, or a cross-cutting UI rule like the single-language rules above. Small local edits (a string, one styling tweak, a test) don't need it.
- Report the findings and what you did with each; if a finding is a false positive, say why instead of silently dropping it.
